Theme 05: Interruptible Real-Time Agents — Technical Innovation Analysis
Samsung PRISM Generative AI Hackathon, 3rd Edition. Third document in the series, after Pre-Architecture Problem Analysis and System Architecture. References of the form "arch §8.3" point to the architecture document; invariant IDs (P3, W1, K3, …) are defined there and in the analysis.

No implementation code. Every claimed benefit is paired with the metric that would show it. No numbers are reported, because nothing has been measured yet.

1. Limitations of the baseline architecture
The baseline is sound in its core commitments: single writer, read-set validation, one commit gate. Reviewing it against adversarial timing still finds seventeen weaknesses. Three are defects that must be fixed regardless of any innovation (L3, L4, L15). The rest are places where stale work can survive, latency remains higher than necessary, or safety depends on luck in timing.

1.1 Findings
L1 — Transitive invalidation lag. Where: downstream calls bind to derived facts (arch §3.1, §4.3 STEP_OUTPUT); derived facts change only when the upstream call re-runs. Sequence: search_flights(Pune) consumed → derived.selected_flight = F1 → get_seat_map(F1) in flight → user says "Mumbai." The search is invalidated and re-issued, but get_seat_map's read set contains only derived.selected_flight, which has not changed. The seat-map call is not cancelled until the new search returns. If its result arrives first, it is consumed and may be narrated. Affects: Interruption Recovery (late cancellation), Task Completion, quality.

L2 — Staleness by omission. Where: read sets contain only facts used in bindings (arch §3.2). Sequence: search_flights(destination, date) in flight → user adds "only direct flights," which maps to an optional nonstop parameter that was never bound. No fact in the read set changed, so the result is consumed and the final response lists connecting flights. Affects: Task Completion, Interruption Recovery, quality.

L3 — Same-step claim ordering defect. Where: emission order puts SPEAK before TOOL_CALL (arch §5.2), while the truth rule requires an IN_PROGRESS claim to reference an in-flight call (arch §15.3). Sequence: the end-of-turn step intends ACK "searching now" and call c1. Validated in order, the ACK references a call that does not exist yet and is rejected, losing latency. If the rule were relaxed and c1 then failed schema validation, the ACK would be a false claim. Affects: Response Latency, quality, Safety & Protocol. Defect.

L4 — Timer liveness under a stepped clock. Where: deadlines, cancellation inference, re-prompts, and hold timers fire only when harness time passes (arch §13.3). Under clock Model B the harness may be waiting for the agent. Sequence: write b1 is cancelled → CommitGate blocks b2 until b1's deadline infers the cancellation → the mock suppresses results of cancelled calls, so no further event is scheduled → the harness waits for the agent while the agent waits for a timer. Nothing happens until the 120 s cap. Affects: Task Completion. Defect.

L5 — Post-turn corrections against same-step writes. Where: CommitGate G3 requires only a closed floor (arch §7.4). Sequence: "book the 6 pm one" ends at t → b1 emitted at t → "no wait, 8 pm" at t + 150 ms → cancellation race → reconciliation or a double booking. Affects: Safety & Protocol, Task Completion.

L6 — Exact-digest promotion of speculative interpretation. Where: arch §11.3. Sequence: the prefix "book a flight to Pune on Friday" is interpreted; the final chunk is "please." The digest no longer matches, so full re-interpretation runs after end of turn, and both the acknowledgment and any EOT-anchored cancellation wait for a model call under clock Model A. Affects: Response Latency, Interruption Recovery.

L7 — Detector recall on indirect corrections. Where: QuickDetector extracts only exact, high-confidence values (arch §9.2). Sequence: "actually, the later one" while get_seat_map runs for the earlier flight. No value is extracted, so cancellation waits for interpretation. Affects: Interruption Recovery. Residual by design: high precision was chosen over recall.

L8 — Result-to-final-response latency. Where: the Composer runs after the last result, with a 1.5 s fallback deadline (arch §9.4). Effect: longer exposure to barge-in at the end of every task, and pacing gaps. Affects: quality, Task Completion.

L9 — Triage hold serializes valid work behind interpretation. Where: arch §8.3. Even a backchannel ("mm-hmm") holds all speech and new calls until the interpreter returns. Affects: Response Latency (minor), quality.

L10 — Perception claims never expire. Where: arch §10.3–10.5. Watch mode re-analyzes frames only while dependent calls are in flight. Sequence: manual lookup completes → the indicator on the device changes in later frames → the final response, grounded in the old claim, describes a state that no longer exists. Watch mode is also the most compute-intensive part of perception. Affects: Task Completion and quality on visual scenarios.

L11 — Uncalibrated confidence labels. Where: arch §10.5. Conflicts open or not depending on HIGH/MEDIUM labels the vision model verbalizes. Affects: spurious or missing clarifications. Residual.

L12 — Lexical perception triggers. Where: arch §10.4. "What's wrong with it?" while showing a device contains no cue word, so perception waits for the planner to request it. Affects: Response Latency and Task Completion on visual scenarios.

L13 — Fingerprints over strings. Where: arch §7.4. "The 6 am one," "AI 505," and "flight five-oh-five" can yield different canonical arguments for the same booking. Planner-generated identifiers can be fabricated and still pass schema validation. Affects: Safety & Protocol (duplicates escape), Task Completion (argument accuracy).

L14 — Unordered writes in multi-step plans. Where: arch §7.3 limits one write per lineage but does not order writes relative to reads. Effect: writes may be in flight while reads that could change them are pending, lengthening the window in which an interruption finds an irreversible action underway. Affects: Safety & Protocol, Task Completion.

L15 — No distinction between intended and in-progress actions in speech. Where: arch §7.8 emits "Booking the 6 am flight now" in the same step as the gate pass. Once any delay exists between the decision and the emission (L5's remedy introduces one), this wording becomes false. Affects: quality (truthfulness), Floor management. Defect once writes can wait.

L16 — No priority between speculative and critical worker jobs. Where: arch §14.1 caps concurrency without priorities. Under Model A, speculation can delay the interpretation that a pending end of turn needs. Affects: Response Latency.

L17 — Visible speculative reads disabled. Where: arch §11.1 defaults, pending the kit's rules on extra calls (Q6). Long-latency reads cannot start before end of turn. Affects: Response Latency and Task Completion time. Deferred by necessity.

3. Evaluation of each candidate
Scales used: Complexity S (under two days), M (two to four days), L (more); Demo potential Low, Medium, High; Scoring relevance High, Medium, Low, with the category named.

C1. Inert-tail promotion of speculative interpretation
#	Field	Evaluation
1	Problem solved	Exact-digest promotion fails whenever a turn ends with content-free words or a chunk arrives after the last speculative interpretation finished. The full interpretation then runs on the critical path after end of turn (L6)
2	Mechanism	At end of turn, compute the tail: final transcript minus the prefix covered by the latest completed speculative interpretation. Promote that interpretation if QuickDetector finds in the tail no value, no correction, hold, abort, or negation cue, and no token outside an inert lexicon (politeness words, fillers, discourse markers). Otherwise dispatch a tail-conditioned re-interpretation (previous interpretation plus tail), which is a shorter model call. Additional guards: the tail must be empty when a clarification is pending, and a turn that sets commit intent needs two consecutive prefix interpretations with identical act, intent, and slot digests
3	Technical novelty	Incremental processing and early commitment are established in spoken dialogue research (Schlangen and Skantze, 2009). The difference here is that promotion is gated by a deterministic check wired into the same validity machinery as tool calls, so early commitment cannot bypass cancellation or commit rules
4	Core invariant	A promoted interpretation can differ from the full-transcript interpretation only by tail content that carries no value and no change cue
5	Architecture	Changes the promotion rule in TurnManager and TaskController (arch §11.3); adds an inert lexicon to QuickDetector configuration
6	Interruptions	More end-of-turn steps apply interpretation immediately, so EOT-anchored cancellations land in the same step. A correction in the tail always contains a cue or value, so it always forces re-interpretation
7	Virtual time	Under Model A, removes one model call from end-of-turn reactions. Under Model B, no latency change, but fewer decisions happen in worker-completion steps
8	Multimodal	Applies to synthetic chunks from ASR. Disfluencies ("uh") are inert; self-repair markers ("I mean") are cues
9	Tool safety	Stricter promotion for commit-bearing turns limits the risk of acting on a promoted interpretation
10	Latency	Expected reduction in end-of-turn → acknowledgment and end-of-turn → cancellation latency on turns with inert tails
11	Computational cost	Negative: saves model calls
12	Failure modes	A word inert in general is content in context ("fine" answering "Shall I book it?"); mitigated by the pending-clarification rule. A negation outside the lexicon's scope; mitigated by making negation tokens never inert
13	Complexity	S
14	Testability	For every turn in local runs, also compute the full interpretation offline. Measure promotion hit rate and promotion disagreement rate (target: zero disagreements on act, intent, and slots). Ablate end-of-turn latency under the Model A simulator
15	Demo potential	Low alone; Medium as part of a latency timeline
16	Scoring relevance	Medium: Response Latency and cancellation promptness under Model A; negligible under Model B. Clock model must be known before this is prioritized
C2. Prepared response frames with typed holes
#	Field	Evaluation
1	Problem solved	After the last result, the final response waits for a model (L8). Generated text needs heuristic truth checks that can reject valid text or miss subtle fabrication
2	Mechanism	When the last required call of a plan is emitted, dispatch a FRAME job. The model writes the final response in advance as a template with typed holes bound to result paths, using a fixed operator set (field, count, min or max by field, first-k, exists) and branches for non-empty success, empty success, and error. The kernel validates the frame against the tool's output schema, or against the shape of an earlier result from the same tool in this session. When the result arrives, the kernel selects the branch, evaluates holes deterministically, type-checks, renders, and emits FINAL in the same step. The frame's read set includes goal facts and constraints, so a correction drops it. Composer remains the fallback
3	Technical novelty	Template generation and slot filling are old. The contribution is preparing the template speculatively against an in-flight call so the final response becomes event-anchored, and making grounding structural: every data value in the text is the output of a hole evaluated on a consumed result
4	Core invariant	Every entity, number, time, or code in a frame-rendered response is the value of a hole evaluated on a result consumed for the active goal
5	Architecture	New job kind FRAME; ResponsePlan becomes frame input; free-text truth checks remain only for Composer fallback
6	Interruptions	A frame and its result must both be valid in the emission step, so no final response built for superseded values can be emitted
7	Virtual time	Under Model A, result → FINAL latency becomes one kernel step. Under Model B, FINAL moves from a worker-completion step to the result step
8	Multimodal	Holes may reference accepted perception claims, subject to lease validity (C7)
9	Tool safety	Completion wording exists only in the success branch; error results force the error branch, so a failed write cannot be reported as done
10	Latency	Result → FINAL; not the scored latency metric (first substantive speech)
11	Computational cost	One model call per completed plan, as with the Composer, but made earlier; wasted when invalidated
12	Failure modes	No output schema and no earlier result → cannot validate → fallback. Answers requiring reasoning beyond the operator set (e.g., the cheapest direct flight after 5 pm under an unmapped constraint) → fallback. Wrong hole paths → validation failure → fallback. Rigid rendering may lower naturalness
13	Complexity	M
14	Testability	Frame coverage (share of FINALs rendered from frames); frame validation failure rate; result → FINAL latency; truth violations in frame output (target: zero by construction); pairwise naturalness comparison against Composer output on identical results, by blind rating (reported as a proxy for the quality judge, not as a score)
15	Demo potential	High: a frame visibly prepared before the result, filled on arrival; a correction dropping it
16	Scoring relevance	Medium-High: Task Completion (response grounding) and quality (truthfulness). Not Response Latency as the specification defines it
C3. Event-anchored reaction scheduling
#	Field	Evaluation
1	Problem solved	Scored actions (cancellations, first substantive speech, first tool call after end of turn, FINAL) often happen in steps triggered by worker completions. Their timing then depends on model latency and machine load, so latency trails events and traces vary between runs
2	Mechanism	For each harness event the agent can anticipate — end of an open turn, the result of each in-flight call, the answer to a pending clarification — the JobScheduler maintains a reaction slot holding the proposals needed to act on it: prefix interpretation (C1), response frame (C2), perception for an open visual question (C13), acknowledgment phrase. Slots are filled in order of imminence and criticality (C16). When the event arrives, the kernel only validates and selects. The design objective is reported as the event-anchored ratio: the share of scored actions emitted in steps triggered by harness events
3	Technical novelty	The idea resembles precomputation and branch prediction. The contribution is treating event anchoring as an explicit, measured objective for a trace-scored agent, and organizing all speculation around it rather than as independent optimizations
4	Core invariant	A prepared reaction takes effect only if its read set is valid in the step of the event it anticipates; otherwise the normal path runs
5	Architecture	JobScheduler gains a reaction-slot table and a priority rule; emission unchanged
6	Interruptions	Slots are invalidated like any proposal and refilled for the new state after triage
7	Virtual time	Directly targets Model A latency and run-to-run variance; under Model B it improves robustness if the harness does not wait for speculative jobs
8	Multimodal	Perception for open questions is a slot, so claims can be ready at end of turn
9	Tool safety	None directly; writes still pass the commit barrier
10	Latency	All event → action latencies
11	Computational cost	More speculative model calls; waste rate is measurable and bounded by one job per slot
12	Failure modes	Compute contention under Model A (mitigated by C16); hosted API rate limits; wasted calls when predictions fail often
13	Complexity	M
14	Testability	Event-anchored ratio; per-trigger latency distributions; trace variance across 20 runs of each scenario under the Model A simulator; speculative waste rate
15	Demo potential	Medium: a timeline in which actions line up with the events that caused them
16	Scoring relevance	Medium: Response Latency and cancellation promptness, mainly under Model A
C4. Planner bypass for single-tool intents
#	Field	Evaluation
1	Problem solved	A new goal waits for a planner call before its first tool call
2	Mechanism	If the interpretation names a candidate tool that is READ and whose required parameters are all committed, emit it as a single-step plan while the planner runs; keep it if the accepted plan contains the identical step, cancel it otherwise
3	Technical novelty	Low; common routing shortcut
4	Core invariant	Bypass calls are read-only and cancelled unless the accepted plan contains an identical step
5	Architecture	Adds a path in TaskController
6	Interruptions	Bypass calls are cancelled like any other
7	Virtual time	Benefit only under Model A
8	Multimodal	None
9	Tool safety	Read-only by construction
10	Latency	End of turn → first tool call, which is not the scored latency metric
11	Computational cost	None
12	Failure modes	Visible wasted calls and cancellations whenever the planner disagrees, with unknown trace penalties (Q6)
13	Complexity	S
14	Testability	End of turn → first call latency; bypass disagreement rate
15	Demo potential	Low
16	Scoring relevance	Low. The baseline already plans speculatively on transcript prefixes, and C1 makes those plans usable at end of turn. Rejected
C5. Provenance-closed invalidation with value-based early cutoff
#	Field	Evaluation
1	Problem solved	Derived facts outlive the slot values that produced them, so downstream in-flight calls are cancelled late and their results can be consumed (L1)
2	Mechanism	Every derived fact stores the read set of the call whose result produced it (its provenance). The dependency index links provenance keys to derived facts. When a provenance fact changes, the derived fact is marked RETRACTED in the same apply phase, recursively along the plan. Retraction invalidates all dependents, so downstream in-flight calls are cancelled in the same step as the correction. When the upstream step re-runs and produces a derived fact with the same digest, the retraction clears; completed downstream results whose read sets match become valid again and are reused rather than re-run (early cutoff). In-flight downstream calls are never kept alive in the hope of a cutoff: cancellation promptness takes priority over saving work
3	Technical novelty	Dynamic dependency tracking and early cutoff come from incremental build systems and self-adjusting computation (Acar, 2005; Mitchell, 2012; Hammer et al., 2014). The application to an agent's tool plan, with an eager-cancel / lazy-reuse split dictated by a cancellation grace period, is uncommon in agent orchestration, which typically re-plans per turn
4	Core invariant	After every apply phase, no non-retracted derived fact has a provenance read set that is invalid
5	Architecture	FactStore gains provenance; InvalidationEngine gains transitive retraction; ResultRouter records provenance
6	Interruptions	Cancellation of transitive dependents happens in the step of the correction. Reversions and corrections that do not change upstream outputs reuse completed downstream work
7	Virtual time	Independent of clock model. Cancellation delay for chained calls drops from roughly one upstream tool latency to one step
8	Multimodal	Perception claims used as tool inputs become provenance, so a changed claim cascades exactly like a changed slot
9	Tool safety	Writes downstream of a retracted fact are blocked immediately, preventing a booking with a flight ID from a superseded search
10	Latency	No added latency; reuse removes some re-runs
11	Computational cost	Index size proportional to derived facts times provenance size; small
12	Failure modes	Over-retraction when provenance includes facts not semantically used (harmless but wasteful). False cutoff if result canonicalization drops meaningful fields; mitigated by digesting the full canonical result
13	Complexity	M
14	Testability	Chain scenarios (search → detail → booking) with corrections at swept offsets. Metrics: transitive cancellation delay; stale downstream consumptions (target zero); re-executed steps per correction. C17 should find L1 in the baseline and not with C5
15	Demo potential	High: baseline and C5 side by side on the same interleaving
16	Scoring relevance	High: Interruption Recovery (prompt cancellation, no stale re-runs); Task Completion; Safety (writes blocked on stale identifiers)
C6. Schema-complete read sets
#	Field	Evaluation
1	Problem solved	A result stays valid after the user adds a constraint the call never read (L2)
2	Mechanism	A call's read set records every parameter in its tool's schema, bound or not; unbound parameters record absence. Setting a previously absent parameter changes absence to a value and invalidates the call. Goal-level constraints that map to no tool parameter are recorded in the read sets of response frames and of steps that select among results, so the answer reflects them even when the tool cannot. Policy absence_sensitivity (default: user-sourced facts only) prevents a later perception claim for an optional parameter from retroactively invalidating completed work
3	Technical novelty	This is the phantom problem from databases, handled there by predicate locks and serializable snapshot isolation (Eswaran et al., 1976; Cahill et al., 2008). Treating an unset optional tool parameter as a predicate read is the transfer
4	Core invariant	A consumed result was produced under the current value, including absence, of every parameter its tool accepts
5	Architecture	ArgBinder records absence entries; DependencyIndex indexes absent keys
6	Interruptions	Additions ("only morning flights") cancel and re-bind in the same step instead of answering the old question
7	Virtual time	Independent
8	Multimodal	Governed by absence_sensitivity to avoid perception-driven churn
9	Tool safety	A user addition before a commit changes the write's arguments before the gate passes
10	Latency	May cause re-runs that turn out unnecessary; those re-runs are required for correctness
11	Computational cost	Read-set size grows with parameter count; negligible
12	Failure modes	Interpreter slot names that do not match parameter names produce no absence change (same exposure as the baseline). Over-invalidation when an optional parameter is irrelevant to the result
13	Complexity	S
14	Testability	Addition-after-call scenarios. Metric: omission escapes, defined as consumed results whose tool had an optional parameter set later in the same goal before FINAL (target zero)
15	Demo potential	Medium-High: "only direct flights" arriving mid-search
16	Scoring relevance	Medium-High: Task Completion (argument and grounding correctness); Interruption Recovery (cancellation, updated snapshot). Whether hidden scenarios contain additions is unknown; the public suite's "clarifications" and "interruptions" make it plausible
C7. Evidence leases
#	Field	Evaluation
1	Problem solved	Perception claims never expire (L10), and baseline watch mode spends compute continuously while remaining blind after calls complete
2	Mechanism	Each accepted claim carries a lease determined by its question mode. AT_UTTERANCE claims are pinned to their anchor frame and never expire, because freshness is irrelevant to what the user pointed at. CURRENT_STATE claims expire after lease_frames newer frames or lease_ms of harness time since capture, whichever comes first. Leases are checked only at points of use: the commit barrier (C9), emission of a statement that relies on the claim, and binding of a new call. An expired lease at a point of use triggers renewal: one perception job on the newest frame for the same question. Agreement renews the lease and raises confidence by one band (replacing stability_k). Disagreement at HIGH confidence changes the claim fact and cascades (C5); disagreement at MEDIUM opens a conflict. Reads may proceed on an expired lease with hedged wording; writes and unhedged statements may not. Watch mode is removed
3	Technical novelty	Leases bound staleness in distributed caches (Gray and Cheriton, 1989). Applying time- and frame-bounded leases to perceptual claims, renewed only at points of use, turns freshness from a continuous perception cost into an on-demand check
4	Core invariant	No write and no unhedged statement relies on a CURRENT_STATE claim whose lease has expired at the moment of emission
5	Architecture	Claim gains a lease; PerceptionScheduler loses watch mode and gains renewal jobs; truth checks consult leases
6	Interruptions	Renewal jobs are ordinary jobs with read sets; a goal change voids them
7	Virtual time	lease_ms is in harness time. Under Model B, where time may stand still, the frame-count bound still works
8	Multimodal	Core purpose
9	Tool safety	Prevents writes (e.g., a support ticket naming a device state) based on outdated visual evidence
10	Latency	Adds one perception call at points of use with expired leases; removes continuous watch analysis. Net effect must be measured
11	Computational cost	Proportional to points of use with expired leases, rather than to frames arriving during in-flight periods
12	Failure modes	Mis-tuned parameters (too short: excess renewals; too long: staleness). No newer frame available: renewal impossible → hedge or request a view. A single noisy frame at MEDIUM confidence opens a conflict rather than flipping the claim
13	Complexity	M
14	Testability	Synthetic frame sequences in which visible state changes after a lookup. Metrics: stale-evidence groundings, computed offline by analyzing every frame and checking claims used at emission (target zero for writes); perception calls per scenario versus watch mode
15	Demo potential	High in a visual scenario
16	Scoring relevance	Medium-High on visual scenarios: Task Completion (grounding) and quality (truthfulness), with the hidden-set multimodal weighting. Visual scenarios are 20% of the set; the effect is concentrated there
C8. Claim-typed atomic emission
#	Field	Evaluation
1	Problem solved	Speech can claim work that a later action in the same step has not yet made true, or that the gate then rejects (L3). Speech cannot distinguish an intended write from one in progress (L15)
2	Mechanism	(a) Two-phase emission: validate the entire step batch first, allowing claims to reference actions in the same batch; if a referenced action fails validation, dependent utterances are re-rendered at a lower claim grade or dropped before anything is written; then write in order. (b) Typed claims on an epistemic ladder: UNDERSTOOD < INTENDED < IN_PROGRESS < RESULT < EFFECT_DONE, plus EFFECT_FAILED and EFFECT_UNKNOWN. Every template and frame hole declares the grade it realizes, and wording follows the grade: "I'll book," "Booking," "Booked." The gate checks each claim against ledger state after the batch. Lexicon checks remain only for free-form model text
3	Technical novelty	Speech-act typing is old in dialogue systems. The application is binding epistemic grade to ledger state and validating it atomically with the actions it describes
4	Core invariant	Every emitted claim's grade is supported by ledger state that holds once the whole batch is applied
5	Architecture	EmissionGate becomes two-phase; utterance claims gain grades; FastResponder templates are keyed by grade
6	Interruptions	Cancellations are validated first, so no claim about cancelled work survives into the same batch
7	Virtual time	None
8	Multimodal	Claims resting on MEDIUM-confidence evidence render with hedged wording
9	Tool safety	Removes false "doing" and "done" statements for writes waiting at the barrier
10	Latency	Removes the ACK rejection in L3; otherwise none
11	Computational cost	Negligible
12	Failure modes	Template bank lacks natural phrasing for some grade and intent combinations; model text without declared claims falls back to lexicon checks
13	Complexity	S
14	Testability	Trace checker compares claims with ledger state; mutation tests inject gate rejections and deadline changes (target: zero false claims)
15	Demo potential	Medium
16	Scoring relevance	High relative to effort: quality (truthfulness), Floor management (no false completion claims), Safety & Protocol. Part (a) is mandatory as the fix for L3
C9. Commit-last ordering with a settled commit barrier
#	Field	Evaluation
1	Problem solved	Writes emitted in the end-of-turn step are exposed to corrections that arrive moments later (L5). Writes in flight while informing reads are pending lengthen the exposure window (L14). Timers the gate relies on can deadlock under a stepped clock (L4)
2	Mechanism	(a) Commit-last: PlanExecutor defers every WRITE until all READ steps not downstream of it are consumed; consecutive writes form one commit window. (b) Settle barrier: the first write of a window is admissible only when every gate condition holds, σ harness milliseconds have passed since the end of the committing turn with no new user event, leases for evidence-derived arguments are valid (C7), and no interpretation job is pending. (c) Timer liveness: timers are "no earlier than" deadlines; under a stepped clock, if the agent would otherwise be idle with only timers pending and the ClockPort cannot request time advance, the earliest timer fires immediately and is logged as LIVENESS_FIRE. σ then degrades to zero instead of deadlocking. (d) Speech about a waiting write uses INTENDED claims (C8)
3	Technical novelty	Sagas order and compensate long-running transactions (Garcia-Molina and Salem, 1987); debouncing is common. The specific insight comes from the evaluation contract: Response Latency measures the first substantive spoken action, not write timing. The agent can therefore hold the floor with speech immediately and delay the irreversible effect, paying nothing in the latency metric
4	Core invariant	A write is emitted only after a quiet interval σ following the turn that committed it, and only when no read remains that could change its arguments or its necessity
5	Architecture	CommitGate G3 extended; PlanExecutor ordering rule; TimerWheel liveness rule; optional request_advance capability in the Model B ClockPort
6	Interruptions	Corrections within σ of end of turn reach the agent before the write exists. Writes are never in flight while reads that inform them are pending
7	Virtual time	σ is harness time. Under Model B it protects only if the harness delivers scheduled events before firing agent timers; otherwise the liveness rule applies. Effectiveness must be measured separately per clock model
8	Multimodal	Lease renewal happens inside the barrier
9	Tool safety	Core purpose
10	Latency	Adds σ, plus any lease renewal, to write emission. First substantive speech is unchanged, because the INTENDED acknowledgment is emitted at end of turn. Must be verified with the latency metric
11	Computational cost	None
12	Failure modes	σ too long may reorder a write relative to the next scripted event and hurt Task Completion. σ too short gives no protection. A slow unrelated read delays writes; capped by commit_wait_cap_ms. Liveness fires nullify σ
13	Complexity	S–M
14	Testability	Sweep correction offsets from −500 to +1000 ms around end of turn in write scenarios, for σ ∈ {0, 150, 300, 600}. Metrics: writes later cancelled or reconciled; duplicates; write exposure window (first write emission to last write result); added write delay; first-speech latency (target: unchanged); liveness fires
15	Demo potential	High: "wait, the 8 pm one" 200 ms after "book it." The baseline has to reconcile; C9 never books the 6 pm flight
16	Scoring relevance	High: Safety & Protocol (zero duplicates), Task Completion, Interruption Recovery (fewer irrecoverable states). The liveness rule is mandatory as the fix for L4
C10. Reference-bound write arguments
#	Field	Evaluation
1	Problem solved	String fingerprints miss duplicates under paraphrase, and planner-produced identifiers can be fabricated (L13)

5. The selected set
5.1 Technical identity
Prepare early. Check at the point of use. Commit late.

A full-duplex agent fails in two opposite ways: it reacts after the event, or it acts on information that stopped being true. The selected mechanisms separate when work is done from when it takes effect, and attach to each piece of work an exact, cheap condition under which it may take effect.

Mechanism	Parts	What it moves or checks
M1 Prepared reactions	C3 event-anchored scheduling (with C13, C16); C1 inert-tail promotion; C2 response frames	Moves model work before the event it reacts to, so the kernel only validates and selects when the event arrives
M2 Complete validity conditions	C5 provenance-closed invalidation with early cutoff; C6 schema-complete read sets; C7 evidence leases; C8 claim-typed atomic emission	Makes the condition for taking effect exact: transitive (derived facts), negative (absent parameters), temporal (perception), and epistemic (what speech may claim)
M3 Settled commits	C9 commit-last ordering, settle barrier, timer liveness; C10 reference-bound arguments	Moves irreversible effects after everything that could change them, and ties their arguments to observed entities
M4 Adversarial schedule exploration	C17	Checks that the conditions hold across interleavings, not in one lucky ordering
5.2 Why these belong together
Each mechanism is unsafe or weak without the others.

M1 without M2 is dangerous. Prepared work is computed earlier and therefore has more time to go stale. Early preparation is only safe if staleness is detected exactly, including through derived facts and absent parameters.
M2 without M1 costs latency. Precise invalidation produces more re-computation. If re-computation happens on the critical path after events, recovery gets slower; with M1 it is already underway.
M1 without M3 exposes writes. A faster agent reaches irreversible actions sooner, sometimes before the user has finished correcting. M3 decouples the speed of speech from the timing of effects.
M3 depends on M2. The barrier checks leases (C7) and blocks on retracted references (C5, C10); speech about waiting writes needs claim grades (C8).
M4 is what makes the other three claims rather than hopes. Every mechanism above is a timing argument, and timing arguments are verified by exploring timings.
The unifying technical idea is transactional: every action carries a validity condition, the condition is checked at the moment of effect, and the expensive parts of the work are scheduled so that checking is all that remains when the moment arrives.

5.3 What was left out and why
C4, C11: low measurable value over existing mechanisms.
C12, C15: value depends on data or kit rules not yet available; switches remain in the design.
C13, C14, C16: kept as supporting details, not as claims of innovation.
No extra agents, no larger models, no decorative interface. None addresses a scored failure mode above.

7. Technical story
7.1 The narrative
Problem. In a full-duplex conversation, the facts an agent acts on change while it is acting. The evaluator scores the trace: whether each action was still valid at the moment it was taken, and how quickly the agent responded.

Baseline limitation. A conventional asynchronous agent checks validity when work starts, does its model work after events arrive, and treats an issued tool call as done. Stale work therefore leaks through three gaps: through derived values, through constraints the call never read, and through old camera frames. Reactions trail events by model latency. Irreversible actions go out while the user is still correcting.

Architectural insight. Treat every action as a transaction whose validity is checked at the moment it takes effect, against a complete dependency set. Do slow work before the event it reacts to. Take irreversible effects last. The scoring rules make the last step affordable: latency is measured to the first spoken action, not to the write.

Mechanism.

Prepared reactions: interpretations, response frames, and perception are ready before end of turn or before the result arrives.
Complete validity conditions: dependencies are transitive, include absent parameters, carry leases for visual evidence, and grade what speech may claim.
Settled commits: writes wait for a quiet interval and for every read that could change them, and name only observed entities.
Adversarial schedule exploration: thousands of interleavings per scenario, checked against invariants derived from the rubric.
Measurable effect. Cancellation delay for dependent calls, stale consumptions, omission escapes, stale-evidence groundings, false claims, duplicate and reconciled writes, speech latency, and invariant violations under exploration — each reported for baseline and full system, under both clock models. (Values to be filled from section 6.3.)

Why it matters. These failures map onto the score: Interruption Recovery (35%) rewards prompt cancellation and no stale re-runs; Task Completion (40%) rewards grounded answers with correct arguments; Safety & Protocol (10%) requires zero duplicate state changes. They also map onto the specification's own use cases: a route computed for the old destination, a double booking, a manual lookup for the wrong device state.

7.2 One sentence
We treat every agent action as a transaction checked at the moment it takes effect, prepare the slow work before the events it reacts to, and delay irreversible effects until the conversation has settled — and we verify it across thousands of adversarial timings.

7.3 Thirty-second version
Users interrupt while an agent is working, so the information behind every action can change mid-flight. Our agent records exactly what each action depends on — including values derived from earlier results, constraints a tool never received, and how fresh its camera evidence is — and checks those dependencies at the instant of acting. Slow reasoning is done before the event that needs it, so reactions happen when events arrive. Bookings and other irreversible actions wait for a short quiet interval, which costs nothing in the latency score because speech continues immediately. We test all of this by replaying each scenario under thousands of timing variations and checking invariants taken from the scoring rules.

7.5 README section draft
Design highlights

Validity at the point of use. Every tool call, prepared response, and perception claim records exactly what it depends on. Dependencies include facts derived from earlier results (so a correction cancels dependent calls in the same step), tool parameters that were left unset (so an added constraint invalidates the answer), and time-bounded leases on camera evidence. Nothing takes effect unless its dependencies still hold at that instant.

Prepared reactions. Transcript prefixes are interpreted while the user speaks; final responses are prepared as typed templates while the last tool call runs. When the triggering event arrives, the coordinator only validates and emits.

Settled commits. State-changing calls run after all reads that could change them, after a short quiet interval following the user's request, and only with identifiers taken from observed results or the user's own words. Speech acknowledges the intent immediately, with wording graded to what has actually happened.

Adversarial schedule exploration. A deterministic simulator replays each scenario under systematic and randomized timing variations. Invariants derived from the scoring rules are checked on every schedule; failing schedules are minimized and kept as regression tests.

See docs/measurements.md for results under both clock models.

7.7 Jury questions and prepared answers
Isn't this just optimistic concurrency control? The validation step is. The contribution is what goes into the read set for an agent: derived facts with their provenance, absent tool parameters, leases on perception, and graded speech claims. It is also scheduling work so that validation is all that remains when events arrive. OCC alone would still leak stale work through each of those gaps.

What happens if the harness pauses the clock while your agent computes? Correctness mechanisms (M2, M3, M4) do not depend on the clock model. Latency mechanisms (M1) matter mainly when agent compute advances time. We measure both configurations and report them separately. The timer liveness rule exists specifically because a paused clock can otherwise deadlock timer-based logic.

Doesn't the settle interval hurt latency? It delays the state-changing call, not speech. The specification measures latency to the first substantive spoken action, and the acknowledgment is emitted at end of turn. The metric table includes speech latency as a guard; if it changes, the claim is wrong.

How do you know this works on hidden scenarios? We do not know the hidden score. We know invariant violation rates under controlled adversarial timings, across scenario families built from the evaluation's stated emphases. That is evidence about robustness, not a score prediction.

Why not a larger or faster model? Most of the failures above are coordination failures that a perfect model would still commit: stale transitive work, unread constraints, writes during corrections. Model speed matters for one mechanism (M1) and only under one clock model.

Do false cancellations hurt you? They can. The detector acts only on high-precision matches, and every false cancellation is logged and counted. The trade-off is reported: cancellation delay against false-cancellation rate.

What does multimodal support cost? Perception runs only for questions tied to the active goal and, for freshness, only at points of use. We report perception calls per visual scenario against the continuous watch-mode alternative.

What is new here, honestly? The individual techniques are established: incremental computation, predicate reads, leases, sagas, randomized concurrency testing. The combination, and its derivation from a trace-scored full-duplex agent's failure modes, is what we contribute. We state the lineage in the documentation.

What if the kit defines duplicates or snapshots differently than you assumed? Those are settings, not structure. The duplicate key, snapshot carrier, cancellation anchor, and clock model are configuration with safe defaults.

Why not use an existing agent framework? Frameworks we have seen coordinate at turn boundaries and treat an issued tool call as done. The scoring requires validity at the moment of each action, which needs a single-writer coordinator with dependency tracking.
