Theme 05: Interruptible Real-Time Agents — System Architecture
Samsung PRISM Generative AI Hackathon, 3rd Edition. Companion to Theme 05 — Pre-Architecture Problem Analysis. Invariant IDs T, S, P, W, O, M, C refer to section 14 of that document; this document adds kernel invariants K. Appendix questions Q1–Q16 refer to its Appendix A.

This is a design, not an implementation. It is specified tightly enough that an implementer should not need to make structural decisions, only to fill in behavior at the stated interfaces.

0. Design stance
Four commitments shape every later decision.

One writer, serialized. A single coordination kernel owns all session state and applies every event in a deterministic order. Every other component proposes; none mutates.
Optimistic work, validated at commit. Slow work runs concurrently against a frozen copy of the state it needs and records exactly what it read. The kernel accepts the output only if everything it read is still true. Invalidation becomes a lookup, not a judgment.
Reads may be tried; writes happen once. Speculation, parallelism, and retries are permitted for read-only tools. State-modifying calls pass a single gate, require committed user intent, and are recorded in an effect ledger before emission.
Unknowns live in adapters and policies, not in structure. The evaluation kit is unreleased. Each open question from the analysis maps to an adapter or a policy setting with a stated default (section 20). Answering a question changes a setting, not the architecture.
What the system is not: an LLM loop that calls tools. No language model emits to the harness or mutates state. Models are workers whose outputs are proposals.

2.2 Interfaces
All messages are immutable records. Field lists are normative; names may be adapted, but nothing may be removed.

InputEvent (Ingress → Mailbox) event_id, seq (arrival order), ts (harness timestamp), type ∈ {TEXT_CHUNK, END_OF_TURN, AUDIO_CLIP, VIDEO_FRAME, INTERRUPTION, TOOL_RESULT, TOOL_MANIFEST, SCENARIO_END if provided}, payload (decoded, typed per event type), raw_ref (for logging).

InternalEvent (kernel, workers, timers → Mailbox) event_id, seq, ts = ClockPort.now() at insertion, type ∈ {WORKER_RESULT, TIMER_FIRED, EMIT_REJECTED, MALFORMED_INPUT, SYNTHETIC_CHUNK}, payload.

Job (JobScheduler → worker) job_id, kind ∈ {INTERPRET, PLAN, COMPOSE, VISION, ASR}, speculative (bool), view (copied subset of facts, catalog, evidence references the job needs), read_set, input_digest (e.g., transcript prefix digest), question (for VISION), cancel_token.

WorkerResult (worker → Mailbox) job_id, status ∈ {OK, FAILED, ABORTED}, proposal (one of the proposal types below), diagnostics.

Proposal types

InterpretationProposal: TurnInterpretation (section 4.6) + read_set + input_digest.
PlanProposal: Plan + read_set (includes goal.active and the goal's plan_rev).
CompositionProposal: utterance_text + response_plan_id + read_set.
PerceptionProposal: observation_id + claims[] + question_id + read_set.
TranscriptProposal: segments[] with capture offsets (converted by the kernel into SYNTHETIC_CHUNK events).
Action (kernel → EmissionGate) action_id, kind ∈ {SPEAK, TOOL_CALL, CANCEL, CLARIFY, FINAL}, utterance (for speech kinds: utt_kind, text, claims[]), call (for TOOL_CALL: call_id, tool, args), cancel_target (call_id), snapshot (when attached), trigger_event_id, read_set.

EmitReport (EmissionGate → kernel, synchronous return) Per action: EMITTED with emitted_ts, or REJECTED with reason_code. Rejections are also posted as EMIT_REJECTED for the next step.

ToolCatalog get(tool_name) → ToolSpec{name, description, params_schema, output_schema?, mutability ∈ {READ, WRITE}, mutability_source ∈ {DECLARED, DEFAULTED}, status ∈ {USABLE, QUARANTINED}, frame_param?}; version.

3. Core model: facts, read sets, and generations
This section is the plan/generation model. Everything that detects stale work depends on it.

3.1 Facts
All session knowledge that any decision depends on is stored as facts.

Field	Meaning
key	Namespaced string (below)
value	Canonical form (normalized strings, ISO dates, sorted structures)
digest	Hash of canonical value
ver	Session revision number at last change
status	HYPOTHESIS, COMMITTED, CONFIRMED, DERIVED, RETRACTED
provenance	Source event IDs or call ID or observation ID; modality; capture timestamp
confidence	HIGH, MEDIUM, LOW (for evidence-derived facts)
The session revision is a single counter incremented on every fact mutation. It orders changes; it is not by itself a validity test.

Key namespaces

Namespace	Examples	Written by
goal.active	value = active goal_id or none	Goal creation, replacement, return, abort
goal.<gid>.intent, goal.<gid>.commit_intent, goal.<gid>.plan_rev	intent label; whether the user expressed intent to act	Interpretation commit; planner acceptance
slot.<gid>.<name>	slot.g2.destination	Interpretation commit; evidence acceptance; carry-over
session.<name>	session.user_name, session.device_model	Interpretation commit (session-scoped facts)
hyp.<turn_id>.<name>	Hypotheses from partial transcripts	QuickDetector; speculative interpretation
turn.<turn_id>.prefix	Transcript prefix digest	TurnManager
result.<call_id>	Canonical result payload	ResultRouter on consumption
derived.<gid>.<name>	derived.g2.selected_flight (mapped from a step output)	PlanExecutor on consumption
claim.<question_id>.<name>	Accepted perception claims	SlotResolver
catalog.version	Manifest version	Manifest reducer
3.2 Read sets
Every unit of work records the facts it depended on: read set = set of (key, ver, digest).

Recorded for: worker jobs, proposals, plan steps, tool calls, pending utterances, held proposals, snapshot-bearing actions.

3.3 Validity rule
A read set is valid if and only if, for every (key, ver, digest) in it, the fact key exists, is not RETRACTED, and its current digest equals digest.

A fact has changed for a read set if its current ver is greater than the recorded ver.

Two tests serve two purposes.

Change (versions) drives the dependency index and invalidation: it is cheap and exact.
Validity (digests) decides acceptance. It uses value equality so that a reversion (Pune → Mumbai → Pune) or a return to a suspended goal makes completed work acceptable again without re-running it (P4).
One exception. A call that has received a cancellation is never consumed, even if its read set later becomes valid again. The trace already shows the cancellation; consuming the result afterward would make the trace internally inconsistent.

Decision D4 — see register, section 19.

3.4 Generations without a global generation counter
There is no single global generation counter used for validity. Generations are expressed as facts:

Coarse generation: goal.active. Every piece of goal-bound work includes it in its read set. Replacing the goal changes its value, which invalidates all goal-bound work through the same mechanism as any slot change.
Fine generation: individual slot and derived facts. A localized correction invalidates only work that read the changed slot.
Plan revision: goal.<gid>.plan_rev is included in every planner proposal's read set, so two planner outputs computed from the same revision cannot both be accepted.
Why not a global epoch: a global epoch would invalidate unrelated work on every correction, forcing restarts that the specification penalizes (stale re-runs) and wasting latency. Why not only fine-grained facts: goal replacement must invalidate everything at once, and modelling the goal as a fact achieves that with no second mechanism.

3.5 Identity and relationships
Goal (goal_id)
 └─ PlanRevision (goal_id, plan_rev)
     └─ Step (step_key)                      stable across revisions
         └─ Call (call_id)                   1..n per step (retry lineage)
             ├─ read_set → Facts
             └─ Result → result.<call_id>, derived.<gid>.* → read by downstream steps
goal_id: g<n>, assigned sequentially per session.
plan_rev: incremented on each accepted plan for that goal.
step_key: digest of (goal_id, tool name, binding template). When a new plan revision contains a step with the same step_key whose resolved arguments are unchanged, the existing step, its call, and its result carry over. This is how replanning preserves valid work.
call_id: <session_prefix>-<counter>, deterministic, never reused (unless policy idempotency_key says otherwise, section 20).
Downstream steps include upstream result facts in their read sets, so staleness propagates through chains automatically.
3.6 How an asynchronous result proves it is still relevant
ResultRouter applies these checks in order. The first check that decides terminates the procedure.

Unknown call_id → log UNMATCHED_RESULT; ignore. (C1, C3)
Call already terminal (duplicate delivery) → log; ignore. (C1)
Payload invalid against output schema (if declared) or generic result shape → treat as tool failure of type MALFORMED_RESULT. (C3)
Call status CANCEL_REQUESTED → status COMPLETED_AFTER_CANCEL; do not consume. If WRITE: effect CONFIRMED, raise reconciliation. (W4)
Call's goal not active → status RETAINED; store result facts under the suspended goal; do not act. If WRITE: effect CONFIRMED, raise reconciliation. (P2)
Call's read set invalid → status STALE; retain for audit; do not consume. If WRITE: effect CONFIRMED, raise reconciliation. (P2)
Otherwise → CONSUMED: write result.<call_id> and mapped derived.* facts; mark step done; if WRITE, effect CONFIRMED; PlanExecutor schedules continuations in the decide phase.
3.7 How snapshots stay correct
The snapshot is never stored as a separate object that could drift. SnapshotProjector computes it at the moment of emission, from the current committed facts of the active goal (section 12). Because the emit phase runs after the apply and invalidate phases of the same step, the snapshot always reflects every ingested event (S3).

5. Event flow
5.1 Event classes and ordering priority
Every event in a step batch is ordered by the tuple (ts, class, seq).

Class	Events	Reducer effect
0	TOOL_MANIFEST	Parse into new catalog version; quarantine invalid tools
1	INTERRUPTION	Floor to user; open turn if none; mark turn as interruption; enter triage if a goal is active
2	TEXT_CHUNK, SYNTHETIC_CHUNK, AUDIO_CLIP, VIDEO_FRAME	Append to turn; run QuickDetector; store evidence
3	END_OF_TURN	Close turn; compute final digest
4	TOOL_RESULT	ResultRouter (section 3.6)
5	WORKER_RESULT	Validate proposal read set; accept, hold, or reject
6	TIMER_FIRED	Timer-specific handling
7	EMIT_REJECTED, MALFORMED_INPUT	Fallback handling and logging
Why this order. At equal timestamps, facts that can invalidate work (manifests, user input) are applied before facts that are subject to invalidation (tool results, worker outputs). Conservative ordering means a result that coincides with a correction is treated as stale rather than consumed and then contradicted. seq breaks remaining ties in queue arrival order, which is deterministic under replay. (T2)

5.2 The kernel step
Wake on mailbox event or due timer

Drain mailbox and collect due timers

Order batch by ts then class then seq

APPLY reducers mutate facts and ledgers and bump versions

INVALIDATE dependency index marks affected calls jobs holds and utterances

DECIDE task controller then plan executor then commit gate then clarification then perception then fast responder

EMIT gate validates stamps and writes in fixed order

LOG one decision record for the step

Phase	What happens	Rules
1. Drain	Take every event currently in the mailbox plus timers whose due time ≤ now()	Batching events that arrive close together means decisions are made once, on the latest state
2. Order	Sort by (ts, class, seq)	Section 5.1
3. Apply	Run reducers in order; each fact mutation increments the session revision	No emission; no worker dispatch
4. Invalidate	For every changed fact key, look up dependents; mark calls INVALIDATED_PENDING_CANCEL, abort jobs, drop held proposals and unsent utterances whose read sets are now invalid	Pure marking; decisions come next
5. Decide	Components run in the fixed order shown; each reads the post-invalidation state and appends intended actions; dispatches jobs	No component sees an action decided later in the same step; order is fixed for determinism
6. Emit	EmissionGate validates and writes intended actions in the emission order below	Emission is synchronous; there is no buffer in which an action could become stale (K3)
7. Log	Append the step record	Section 16
Emission order within a step: CANCEL → SPEAK (ACK, REPAIR, PROGRESS, HOLD, INFORM) → TOOL_CALL → CLARIFY → FINAL.

Cancellations first, because promptness is scored (Interruption Recovery). Acknowledgments next, because latency is measured to the first substantive spoken action. Tool calls next, because their emission time starts the mock latency. Clarifications and final responses last, because they conclude the step's reasoning.

Kernel step budget. Target ≤ 5 ms wall time per step. The only non-trivial in-kernel computations are QuickDetector matching, dependency lookups, schema validation, and template rendering. Exceeding the budget is logged as a performance defect.

6. State machine
6.1 Regions
The agent's control state is split into orthogonal regions, because conversation and task progress change independently.

Region	States	Scope
Floor	USER_TURN_OPEN, USER_TURN_CLOSED	Session
Task	IDLE, LISTENING, UNDERSTANDING, CLARIFYING, PLANNING, EXECUTING, RESPONDING, COMPLETED, FAILED, TRIAGE, RECONCILING	Active goal
Goal lifecycle	ACTIVE, SUSPENDED, COMPLETED, FAILED, ABANDONED	Each goal
Call lifecycle	Section 7.2	Each call
Effect lifecycle	Section 7.5	Each fingerprint
EXECUTING has two flags rather than substates, because both can hold simultaneously: reads_in_flight and write_outcome_pending.

Floor rule. No SPEAK, CLARIFY, or FINAL is emitted while the floor region is USER_TURN_OPEN (policy speak_during_open_turn, default OFF). Talking over the user harms naturalness and usually refers to soon-to-change information.

7.4 CommitGate
Every condition must hold. The gate is evaluated in the decide phase each step while a WRITE step is ready; a refused step stays Blocked and is re-evaluated when any blocking fact changes.

ID	Condition	Protects
G1	Tool exists and is USABLE in the current catalog version	O1
G2	Step's goal is goal.active; call read set valid	P1, P5
G3	Floor is USER_TURN_CLOSED and task state is not TRIAGE	W1 (no commit while the user may be correcting)
G4	Every bound argument comes from COMMITTED, CONFIRMED, or accepted DERIVED facts; none HYPOTHESIS; no OPEN conflict on any argument	W3, M2
G5	goal.<gid>.commit_intent is true	Prevents unrequested state changes
G6	No effect with the same fingerprint in PENDING, CONFIRMED, or UNKNOWN	W1 (duplicates)
G7	No effect in the same lineage in PENDING or UNKNOWN; if one is CONFIRMED with different arguments, route to ReconcilePolicy instead of emitting	W1 (double booking), W2
G8	Arguments validate against the tool schema	O1
G9	No intended action in the current step with the same step_key and fingerprint	Idempotent proposal handling
When all hold: write effect PENDING (lineage, fingerprint, call_id) in the decide phase, then emit. If the EmissionGate rejects the call, the effect becomes FAILED with reason LOCAL_REJECT; nothing reached the harness.

Fingerprint. Digest of tool name plus canonical arguments. Canonicalization: keys sorted; strings trimmed and whitespace-collapsed; enum values matched to schema spelling; dates and times in ISO form; numbers normalized. Policy duplicate_key can switch the definition (section 20) once the kit defines a duplicate.

Why commit intent is required. The harness scripts user events. A plan that concludes a booking is useful when the user only asked to search would issue an unrequested state change that no scenario can justify. The cost is that some scenarios may need an explicit confirmation turn; the interpreter treats imperative requests ("book the 6 pm flight") as commit intent, so explicit requests need none.

7.6 ReconcilePolicy
Raised when a WRITE effect exists that the current intent does not want (superseded arguments, abandoned goal) or whose outcome is unknown.

7.7 Tool catalog handling
Parsing. Each tool is validated independently. Required: name, parameter schema parseable as JSON Schema subset (types, required, enums, formats), mutability. A tool failing validation is QUARANTINED (not callable) and logged; the rest of the manifest is used.

Mutability. Taken from the declared field (name set by policy mutability_field once the kit is known). Missing or unrecognized → WRITE, mutability_source = DEFAULTED (W5). Description heuristics may upgrade a declared READ to WRITE when the description contains strong mutation verbs (policy mutability_upgrade_heuristic, default ON); they never downgrade.

Duplicate tool names. The first definition in manifest order is kept; later ones are quarantined. Deterministic.

Unseen tools. No component contains a tool name. The Planner receives names, descriptions, and schemas; ArgBinder uses schemas; mutability comes from the catalog. Frame-accepting parameters (image type, frame identifier) are detected from schema and marked frame_param.

Manifest updates. Each manifest event creates a new catalog version. Plan steps and calls include catalog.version and a per-tool digest in their read sets. Steps whose tool changed or disappeared are invalidated. In-flight calls to removed tools stay tracked; their results are processed normally.

8. Interruption handling, cancellation propagation, plan invalidation
8.1 Propagation algorithm
Triggered in the invalidate phase whenever a fact changes.

Collect changed keys from the apply phase.
For each key, fetch dependents from DependencyIndex.
For each dependent, re-evaluate its read set with the validity rule (a changed version with an equal digest is still valid).
Mark invalid dependents by type:
Dependent type	Mark	Decide-phase action
In-flight READ call	INVALIDATED_PENDING_CANCEL	Emit CANCEL this step
In-flight WRITE call	INVALIDATED_PENDING_CANCEL	Emit CANCEL this step; effect stays PENDING; start reconciliation tracking
Proposed, held, or blocked call	DISCARDED	None
Worker job	ABORTED	Signal cancel token; its eventual result is rejected by read set anyway
Held proposal	Dropped	None
Unsent utterance	Dropped	FastResponder may produce a replacement
Plan step	STALE	Rebinder or Planner produces replacement (section 8.4)
Clarification pending	VOID if its targets changed by other means	None
Conflict	VOID if a candidate's source fact was retracted or its step removed	None
Unregister released read sets from the index.
Cost is proportional to the number of affected dependents, not session size. This is what allows cancellation in the same step as the invalidating fact change.

8.2 When facts change in response to an interruption: cancellation anchors
The analysis identified an unresolved tension (its section 5.6): cancellation is due within a few milliseconds, but knowing what changed usually requires interpretation. The architecture offers three anchors, selected by policy cancel_anchor. The EOT anchor is always active; the other two add earlier cancellation.

Anchor	Fact change that triggers cancellation	When it fires	Risk
SIGNAL	On INTERRUPTION, facts hyp.<turn>.at_risk for every user-derived slot are set, invalidating reads that depend on user slots	Same step as the signal	Cancels valid reads on backchannels; re-issue may count as re-run [Q2, Q6]
CHUNK (default)	QuickDetector writes a HIGH-confidence hypothesis that differs from a slot an in-flight call depends on, and a correction or interruption context exists; the kernel treats that hypothesis as invalidating for in-flight calls (not for committed facts)	Same step as the chunk containing the new value	Misses corrections the detector cannot parse; those are caught at EOT
EOT (always)	Committed interpretation changes facts	Same step as EOT when speculative interpretation is ready for the final digest; otherwise when the interpreter returns	Late when interpretation was not ready
Chunk-anchor rule, precisely. For an in-flight call c and slot s in c's read set, cancel c if all hold:

QuickDetector produced candidate value v for s with HIGH confidence (exact schema enum match, unambiguous parsed date or number with a unique compatible slot, or exact match with a value already seen in this session for the same slot type);
canonical(v) ≠ current value of s;
the turn is an interruption, or occurs while the goal is active, or contains a correction cue.
Write hold cue. For in-flight WRITE calls only, policy write_hold_on_wait_cue (default ON) also cancels on an explicit hold or negation cue addressed to the action ("wait", "hold on", "don't book", "stop"). Cancelling a write that should have proceeded is recoverable: once cancellation is confirmed, the gate admits it again; if it completed anyway, the effect is CONFIRMED and nothing is re-issued. Not cancelling a write that should have stopped is not recoverable.

Why speculative interpretation makes the EOT anchor fast. Interpretation of the transcript prefix runs while the user is still speaking. At EOT, if the final digest equals the digest of the ready interpretation, the kernel applies it in the same step, so EOT-anchored cancellation happens with no model latency (section 11.3).

8.3 Hold mode during triage
On entry to TRIAGE, emissions other than CANCEL are held: new tool calls, speech, clarifications, and final responses produced during triage go to ProposalHold with their read sets. Tool results and worker results continue to be processed, so facts stay current and valid work keeps its results.

On resolution:

Resolution	Held proposals
Backchannel or progress question	Re-validate; release valid ones in emission order
Slot update or addition	Re-validate; invalid ones are already dropped by invalidation; release valid reads; speech is regenerated from the new state rather than released
Goal replacement or return	Drop all held speech; release nothing goal-bound for the old goal
Abort	Drop all
Clarify	Keep holds for work that depends on the question's targets; release the rest
This avoids both failure modes named in the brief: discarding valid work, and emitting work computed before the interruption.

8.4 Replanning: rebind first, plan second
A localized correction usually leaves plan structure intact. The Rebinder handles it without a model call.

Rebind is used when the interpretation is SLOT_UPDATE, every changed slot is bound via FACT bindings in existing steps, and no step's tool choice depends on the changed value (planner marks steps whose tool selection was value-dependent with structure_depends_on).

Rebind procedure. For each STALE step: resolve bindings against current facts; if the fingerprint equals a CONSUMED call's fingerprint whose read set is now valid (reversion), reuse that result; otherwise create a new call. Downstream steps whose upstream result was invalidated become STALE and are re-bound when the upstream is consumed again. plan_rev increments.

Planner is used when the act is NEW_GOAL, ADDITION, or RETURN_TO_GOAL with changed facts; when a changed value affects tool selection; or when rebind fails validation. The planner receives the current plan and the change set, and the kernel carries over steps with matching step_key and resolved arguments (section 3.5).

Trade-off: rebinding is deterministic and fast but cannot notice that a correction makes a different tool appropriate. structure_depends_on marks limit that risk to cases the planner flagged.

8.5 Goal replacement
In one step, on acceptance of NEW_GOAL:

Create g_new; set goal.active = g_new. Every goal-bound read set of the old goal becomes invalid.
Old goal → SUSPENDED; its task state is recorded.
Invalidation cancels in-flight calls of the old goal. Completed results are RETAINED under the old goal.
Carry-over: session-scoped facts remain. Goal-scoped slots are copied to g_new only when the interpretation's slot_deltas reference them, or, under policy slot_carryover = NAME_MATCH_USER_STATED, when the new goal's schema has a parameter with the same name and the old value was user-stated (not derived from an old-goal tool result).
Pending clarifications and conflicts of the old goal → VOID.
Emit ACK for the new goal; snapshot with new intent at the next snapshot-bearing emission.
Any WRITE effects of the old goal that are PENDING or CONFIRMED are reported once, truthfully, when relevant (W4).
Return to a suspended goal. goal.active returns to the old goal_id. Read sets that include it become valid again, so RETAINED results whose other dependencies are unchanged are reused. Cancelled calls are not reused (section 3.3).

8.6 Rapid interruptions
Each interruption and each chunk is applied in order within the step engine; nothing special is needed for correctness. Three rules prevent wasted work:

Speculative interpretation is coalesced per turn (section 11.3), so intermediate prefixes do not each spawn a model call.
A proposal computed for an intermediate state is rejected by read-set validation and never emitted.
The planner is not dispatched while the floor is open during triage unless plan_during_open_turn is ON (default OFF); rebinding, which is cheap, may run.

9.2 QuickDetector specification
Deterministic, schema-aware, high precision. It is allowed to miss; it is not allowed to guess.

Inputs. Current chunk; turn text so far; current catalog; current slot facts; values seen this session (from user statements and tool results, grouped by slot name); scenario reference date if known (policy reference_date_source).

Extractors.

Extractor	HIGH confidence when
Enum values	Exact (case-insensitive) match with an enum value of a parameter of a tool relevant to the active goal
Dates and times	Absolute dates and times parse unambiguously; weekday and relative-day expressions only when a reference date is known
Numbers	Explicit numeral or number word adjacent to a unit or noun matching exactly one numeric parameter
Session entities	Exact match with a value previously seen for a slot name, and only one slot name has that value type
Cues	Lexicons: correction ("actually", "no,", "I mean", "instead", "make it", "change it to", "not … but"); hold ("wait", "hold on", "stop", "don't"); abort ("never mind", "forget it", "cancel everything"); backchannel ("ok", "okay", "mm-hmm", "uh-huh", "yeah", "right", "go on", "sure"); visual ("this", "that one", "here", "look", "see", "screen", "light", "shows")
Outputs. ChunkSignals{values[(slot, value, confidence)], cues[], backchannel_only (bool), visual_reference (bool)}. Only HIGH values produce hypotheses that can drive cancellation or acknowledgments; MEDIUM and LOW values are discarded.

Lexicons are English by assumption; they are configuration, not code.

9.5 ClarificationManager
Ask when (any):

A required parameter of a ready step has no binding source, and evidence cannot supply it;
An OPEN conflict affects arguments of a ready step, and both candidates are MEDIUM or higher;
The interpretation reports an ambiguity whose resolution changes arguments or intent;
A perception target needed by a step is only LOW confidence.
Do not ask when: the target has a value in an ingested user event (including the current open turn after it closes); the ambiguity affects only phrasing; the question would duplicate a pending one.

One question at a time, targeting the item that blocks the most ready steps. The clarification blocks only steps that depend on its targets; unrelated reads continue.

Unanswered clarifications. Policy clarification_reprompt (default ONCE, after clarify_reprompt_ms = 6000 harness ms with floor closed and no user input). Policy unanswered_clarification (default WAIT) never proceeds with a write.

10. Multimodal architecture
10.1 Scope decisions
Included: aligning frames to utterances; question-driven frame analysis; claims with ordinal confidence; conflicts with user statements; ASR when the scenario gives only audio.

Deliberately excluded until the kit shows a need: continuous video understanding, object tracking, prosody or emotion analysis, speaker diarization, non-speech sound classification, ASR on audio that already has a transcript. Each adds latency and failure modes without a stated scoring benefit.

Hesitations and self-repairs in ASR output are preserved verbatim; the Interpreter resolves them. Stripping disfluencies would remove exactly the evidence accessibility scenarios test.

10.3 Evidence representation and time
Each observation carries capture_ts (harness timestamp of the event, treated as capture time [Assumption]) and arrival_ts (step in which it was ingested). Each analysis records the job's completion step. Decisions use capture time for alignment and completion for freshness.

Alignment (correlation). A question created from an utterance has anchor_ts = timestamp of the chunk containing the visual reference (or end of turn if none).

AT_UTTERANCE questions ("what does this light mean") use the latest frame with capture_ts ≤ anchor_ts; if none, the earliest frame after it within align_window_ms (default 1000).
CURRENT_STATE questions ("the light keeps blinking", or a plan step that needs the device's present state) use the latest frame, and may re-analyze newer frames (watch mode).
The Interpreter sets the mode through visual_reference plus tense cues; the default is AT_UTTERANCE.

Freshness. A claim for a CURRENT_STATE question is fresh while no newer analyzed frame for the same question contradicts it. A frame gap (no frames for gap_ms, default 3000) does not invalidate a claim, but a CURRENT_STATE question with a gap longer than gap_ms before a WRITE step triggers a request for a fresh view instead of assuming persistence.

10.4 Perception scheduling
A VISION job runs only when one of these holds.

Trigger	Question	Speculative
QuickDetector visual_reference in an open turn and frames exist	Generic: device identity and salient visible state	Yes (internal only)
A ready or planned step has a required argument whose binding is FRAME(question_id), or a missing required argument the planner marked visual_candidate	Targeted: the argument names and descriptions	No
Watch mode: a CURRENT_STATE question has an accepted claim and a dependent call is in flight, and a newer frame arrives	Same question	No
Tool-side vision. If the relevant tool has a frame_param, the kernel binds the aligned frame's identifier and performs no agent-side analysis for that argument (policy vision_mode = AUTO prefers this). This removes a slow worker from the critical path when the mock environment supports it [Q9].

Coalescing. At most one running VISION job per question. A newer frame for a running question is remembered as latest_pending. When the job completes: AT_UTTERANCE questions ignore latest_pending; CURRENT_STATE questions analyze latest_pending once if watch mode applies.

Cancellation. A VISION job's read set includes goal.active and the question's target facts. Goal replacement or a correction that changes the targets aborts the job through ordinary invalidation. There is no harness action for internal cancellation; the job's cancel token is signalled and any returned proposal is rejected.

Confidence bands. The VisionAnalyzer returns HIGH, MEDIUM, or LOW per claim (verbalized by the model and mapped; treated as ordinal, not calibrated probability).

11.2 Why these defaults
Internal speculation risks only compute. Visible speculation also risks trace penalties that the kit has not defined [Q6]. The defaults therefore take every internal speculation and only those visible speculations whose inputs are already committed. The two OFF settings are the first to enable if the kit shows extra read calls are not penalized.

11.3 Speculative interpretation coalescing
On a chunk: if no INTERPRET job is running for the turn, dispatch one on the current prefix. If one is running, record that the prefix has grown.
When a job completes: if the prefix has grown and the turn is still open, dispatch one new job on the latest prefix.
At EOT: if the running or completed job's digest equals the final digest, wait for or apply it. Otherwise, abort a running job and dispatch a non-speculative job on the final transcript.
This bounds model calls per turn to roughly (turn duration ÷ interpretation latency) + 1 while keeping at most one job in flight.

11.4 Promotion rule for hypothesis-based work
Work that read hyp.<turn>.<name> records the hypothesis value's digest. When the turn's interpretation commits slot.<gid>.<name>, the kernel re-registers such work against the committed fact if and only if the digests are equal. Otherwise the work is invalid and handled by section 8.1.

12. State snapshot generation
12.1 Projection
Snapshot = project(active goal):

intent: value of goal.<gid>.intent, mapped through policy intent_label_source [Q5].
slots: every slot.<gid>.<name> with status COMMITTED, CONFIRMED, or accepted DERIVED; plus session.<name> facts mapped into the goal's parameter names when the goal's tools declare those names. Values are canonical and cast to the schema type of the corresponding tool parameter.
Excluded: HYPOTHESIS facts, MEDIUM or LOW claims not accepted, slots with OPEN conflicts (reported with their user-stated value if one exists, otherwise omitted) [Assumption], suspended goals' slots.
CLEAR deltas remove the slot rather than setting null, unless the schema requires explicit nulls (codec setting).
The projection is computed in the emit phase from current state; nothing is cached (S3).

12.2 When snapshots are emitted
Policy snapshot_carrier [Q5]:

Setting	Behavior
FINAL_ONLY	Snapshot attached to FINAL actions only
ANY_SPOKEN (default if the schema permits a snapshot on non-final actions)	Attached to the first SPEAK, CLARIFY, INFORM, or FINAL emitted after the committed projection changed since the last emitted snapshot
STANDALONE	Separate snapshot action emitted in the same step as the change, if the protocol defines one
A correction therefore produces an updated snapshot no later than the acknowledgment of that correction, which is the behavior Interruption Recovery rewards ("updated state snapshots").

12.3 Validation
EmissionGate checks: intent present and non-empty; slot names belong to the active goal's parameter names or declared session names; types match; no duplicate keys; projection revision is not lower than the last emitted snapshot's revision (monotonicity guard; a violation indicates a kernel defect and is logged, and the current projection is re-computed).

13. Virtual clock
13.1 Three times, kept apart
Time	Source	Used for	Never used for
Logical event time	Harness timestamps on events; ClockPort.now() for internal events and emissions	Ordering, timers, deadlines, alignment, staleness, latency	—
Execution time	Monotonic wall clock, read only by telemetry and the budget watchdog	Performance telemetry; 120 s cap protection	Any correctness decision
Measured latency	Computed from logical timestamps in the trace	Scoring estimates and tuning	Runtime decisions
13.2 ClockPort implementations
Model [Q1]	now()	wake_at(t)	busy(flag)
A — coupled	Harness-provided current time if exposed; otherwise harness time of last event plus scaled monotonic elapsed time since that event (the only permitted derivation)	Schedules a wake-up of the kernel loop at the wall moment corresponding to t	No-op
B — stepped	Harness current virtual time	No wall waiting; timers fire when harness time advances past them	Reports busy while mailbox non-empty or any non-speculative job running; speculative jobs do not hold the clock (policy spec_blocks_clock = OFF)
C — agent-stamped	Harness clock read	As A or B	As A or B
A wake-up hint may use an asynchronous wait internally. That wait only decides when the kernel next looks at the clock; what happens is decided by now() and event timestamps. This is the difference between permitted scheduling and forbidden sleep-based correctness.

13.3 Timers
Timer	Default	Purpose
deadline(tool)	Read 6000 ms, write 12000 ms; per-tool overrides from kit mock latencies	Timeouts, cancel inference
hold_after_ms	2500	HOLD utterance
min_gap_ms	1500	Pacing
clarify_reprompt_ms	6000	Re-prompt
compose_deadline_ms	1500	Template fallback if Composer is slow
dedupe_window_ms	800	AUTO audio mode
All are harness-time timers in the TimerWheel. Under Model B they fire only as harness time advances, which is the intended semantics: no wall-clock timer can cause a retry while virtual time stands still.

13.4 Banned APIs in core modules
time.time, time.monotonic, time.sleep, datetime.now, asyncio.sleep (except inside ClockPort implementations), and loop.time are banned in kernel, store, tool, perception, and conversation packages. Enforced by a static check in CI. Telemetry and the watchdog import a separate, explicitly named module.

13.5 The single wall-clock decision
The budget watchdog triggers transition 32 at watchdog_s (default 105 s) of scenario wall time. It exists because the 120 s cap is a wall-clock constraint [Spec G§6], and forfeiting the final response and snapshot costs more than an early truthful summary. It is logged distinctly and excluded from determinism tests.

13.6 Latency accounting
LatencyMeter computes, for each trigger event, the harness-time difference to the first emitted utterance whose kind is in substantive_kinds (default ACK with at least one UNDERSTOOD claim, PROGRESS, CLARIFY, REPAIR, INFORM, FINAL; HOLD excluded) [Q4]. It reports the metric against every candidate trigger (first chunk, end of turn, interruption signal) until the kit fixes the definition.

13.7 Determinism
Kernel decisions depend only on the ordered event batch and state: deterministic by construction.
Worker outputs are the nondeterministic inputs. Replayer records them per job digest and substitutes recordings in tests.
Under Model A, batch composition depends on arrival timing. TimingSweeper (section 16.5) tests correctness across compositions rather than assuming one.
14. Concurrency model
14.1 What runs concurrently
Unit	Mechanism	Count
Ingress	Async task	1
Kernel step engine	Async task; each step fully synchronous	1
LLM jobs (INTERPRET, PLAN, COMPOSE)	Async tasks using ModelGateway	≤ 1 per kind per turn or goal, plus coalescing
VISION, ASR	Process pool (or thread pool if the inference library releases the GIL)	vision_concurrency, asr_concurrency
Harness tool execution	External; the agent keeps no task per call	Unbounded
Timers	Data in TimerWheel; one wake-up hint	—
Tool calls need no agent-side tasks because results arrive as ordinary input events. This removes a whole class of races between call tasks and the kernel.

14.2 What is serialized
Everything that reads-then-writes session state or emits: reducers, invalidation, all decide-phase components, and emission. Serialization is by construction (single kernel task, synchronous step), not by locks.

14.3 Coordination primitives
Primitive	Where	Why
Mailbox (async queue)	Ingress and workers → kernel	Single entry point; the only cross-task channel into state
Thread-safe loop callback	Pool workers → mailbox	Moving results from pool threads or processes onto the event loop
Cancel tokens	Kernel → workers	Cooperative abort of jobs
Immutable job views	Kernel → workers	Workers never see mutable state; no read locks
No locks on session state. A lock would be both unnecessary (single writer) and harmful (a worker holding it would stall ingestion).

14.4 Cancellability
Cancellable	How	Consequence
Worker jobs	Cancel token; async task cancellation; pool results ignored	Compute waste only
Held proposals, unsent utterances, proposed calls	Dropped in invalidation	None visible
In-flight READ calls	CANCEL action	Visible; scored as prompt cancellation
In-flight WRITE calls	CANCEL action as a request	Effect may still happen; reconciliation handles it
Not safely cancellable	Why	Mitigation
Actions already written to the output queue	Permanent in the trace	Emission happens only after invalidation in the same step (K3)
Completed WRITE effects	Side effect exists	Effect ledger, compensation, truthful INFORM
A kernel step in progress	Atomic by design	Steps are short (≤ 5 ms target)
14.5 State mutation coordination
Workers return proposals with read sets. In the step that ingests the result, the kernel runs the validity rule. Valid → apply (and dispatch follow-on work). Invalid → reject and, if the job kind is still needed, re-dispatch with a fresh view. This is optimistic concurrency control: no waiting for coordination, and conflicts resolved at commit.

14.6 Stale detection
All stale detection reduces to the validity rule over read sets (section 3.3), applied to: proposals (on worker result), calls (on tool result), held proposals (on triage resolution), blocked writes (on gate re-evaluation), and pending utterances (in invalidation).

14.7 Simultaneous events
Ordered by (ts, class, seq) within a batch (section 5.1), then applied sequentially, then decided once. Two events with identical ts and class keep queue arrival order.

14.8 Synchronization deliberately avoided
The kernel never awaits a worker. A step never waits for interpretation, planning, perception, or a tool.
Emission is synchronous inside the step; no second queue sits between decision and harness.
Speculative jobs do not hold the virtual clock under Model B.
Reads are not serialized behind writes; only writes in the same lineage are.

15.3 Truth checks for speech
Every claim in claims[] resolves to a fact, call, or effect whose state supports it: RESULT → CONSUMED result fact of the active goal; EFFECT_DONE → CONFIRMED effect; IN_PROGRESS → call INFLIGHT; UNDERSTOOD → COMMITTED, CONFIRMED, or HIGH hypothesis of the current turn.
Completion wording (configurable lexicon: "booked", "created", "confirmed", "cancelled", "done", "submitted", "reserved", "here are", "I found") is permitted only if a supporting RESULT or EFFECT_DONE claim is present.
Every number, time, date, code, and proper noun in generated text (Composer output or ack_phrase) must match, after normalization, a value in the utterance's claims or the ResponsePlan. Templates are built to satisfy this by construction.
No reference to facts of non-active goals except in INFORM about reconciliation or abort.
Checks 2 and 3 are heuristics against model-generated text; the template fallback always exists, so a false rejection costs naturalness, never truthfulness.

16.3 Metrics
Latency per trigger type (section 13.6); cancel delay (harness ms from the invalidating event to CANCEL); count of calls consumed, stale, retained, completed-after-cancel; duplicate-fingerprint blocks by G6 and G7; held proposals released vs dropped; utterances per goal by kind; truth-check rejections; speculative job hit rate (promoted ÷ dispatched); kernel step duration percentiles; worker latency per kind.

16.4 TraceChecker
Runs on the harness trace plus decision log after each local scenario run. Rules map to invariants (section 17). Example rules:

Every call whose read set was invalidated at step n has a CANCEL in step n (P3).
No two TOOL_CALLs for WRITE tools share a fingerprint unless the first effect is FAILED or CANCELLED_INFERRED (W1).
No emitted action has a read set invalid at its emission step (P1).
Every snapshot equals the projection of committed facts at its step (S3).
No speech between an INTERRUPTION and the next END_OF_TURN (floor rule).
No result of a CANCEL_REQUESTED call appears in any later utterance claim (P2).
Every CANCEL targets an issued, non-terminal call (C1).
No core-module wall-clock calls (static, K5).
16.5 Replay and timing sweeps
Replayer: feeds a recorded input stream and recorded worker outputs; the decision log must be byte-identical across runs under Model B semantics.
TimingSweeper: for each scenario, generates variants that shift tool results and worker completions relative to user events within bounds (before, equal to, after each interruption), and asserts TraceChecker rules on each variant. Correctness must hold across the sweep, not at one timing.
Adversarial generator: produces the failure classes in section 15 of the analysis from templates (correction before and after result, write interrupted, reversion, rapid triple correction, backchannel interruption, goal switch and return, unknown write outcome, quarantined tool, conflicting frame).
17. Invariants and their enforcement
17.1 Kernel invariants (new)
K1. A kernel step never awaits.
K2. Only reducers and kernel decisions mutate session state; workers receive immutable views.
K3. Emission happens in the same step as, and after, invalidation; no buffer exists between decision and output queue.
K4. Every proposal is validated against its read set in the step that ingests it.
K5. No core module reads the wall clock; the watchdog is the sole wall-clock decision.
K6. Every harness-visible action has a decision log record naming the rule that produced it.
