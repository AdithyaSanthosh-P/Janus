## Executive Summary

Janus is a single-writer coordination kernel for an interruptible real-time conversational agent, built for Samsung PRISM Theme 05. The architecture is genuinely novel and well-executed: a synchronous kernel step owns all state mutation; LLM workers (Interpreter, Planner, Composer, Vision, ASR) run async and return proposals validated via optimistic-concurrency read-sets before admission through a CommitGate. This design directly addresses the core challenge — staying responsive while reasoning, running tool calls and LLM reasoning concurrently, and recovering cleanly from user interruptions/corrections without duplicate side effects or false completion claims.

**Overall risk picture**: The codebase demonstrates extraordinary engineering discipline — 359+ deterministic tests, multiple independent review rounds that found and fixed real bugs, a verified Docker build, and a clear version-gating strategy. However, several **critical risks remain for the Samsung submission**:

1. **Default-off safety flags** (C9, C10, settle_barrier, G4 exemption) mean the judged run may not have the intended protections unless explicitly enabled
2. **LiveKit voice path** has unresolved CUDA memory risks on 8GB GPUs and unverified LiveKit Cloud integration
3. **FDB-v3 text-replay strict pass rate is 21%** — suppressed mainly by the G4 gap (Day 2 fix not yet merged to main)
4. **One-command reproduction** for the voice path depends on external FDB checkout/data and unpinned Hugging Face model downloads at container start
5. **Three feature flags default OFF** that are safety-relevant (commit_last_ordering, reference_bound_identifiers, speak_during_open_turn)

The architecture is sound and the implementation largely matches the documented invariants. The critical issues are deployment/configuration decisions and external integration risks, not fundamental architectural flaws.

## Critical Findings

### [CRITICAL] Default-off safety flags leave judged run unprotected
- **Location**: `src/prism_rt/config.py` (lines 136, 146, 82, 266)
- **What happens**: `commit_last_ordering=False`, `reference_bound_identifiers=False`, `speak_during_open_turn=False`, `g4_exempt_undeclared_mutability=False` are all defaults. The CS audit (currentStatus.md lines 258-261) explicitly notes CS-29 and CS-31 are "SOUND mechanism, disabled by default" and "a genuine judged-run configuration risk, not a code defect."
- **Why it is a bug/risk**: The Samsung evaluators will run whatever the submission tag contains. If these flags are not explicitly enabled in the submission config, the kernel will:
  - Allow writes to emit before unrelated reads settle (C9)
  - Accept model-invented identifiers in WRITE calls (C10)
  - Speak over the user while floor is open (CS-28 floor rule)
  - Block all FDB tool calls including reads like `search_flights` for lack of explicit commit_intent (G4)
- **Trigger/path**: Any judged run using the default `Config()`.
- **Evidence from code**: `Config` dataclass defaults; `CommitGate.evaluate()` lines 144-148 (G4 exemption); `FastResponder.decide()` line 87 (floor rule); `PlanExecutor._commit_last_blocked()` line 422 (C9).
- **Likely benchmark/submission impact**: Severe — the FDB-v3 Day 1 run showed 21% strict pass rate primarily due to G4 blocking reads. Without C9/C10, double-booking and identifier hallucination risks are live.
- **Confidence**: 100% — explicitly documented in currentStatus.md and CS audit.
- **Recommended fix direction**: Create a `submission_config()` factory or explicitly set these flags in the FDB-v3 profile (`prism_rt/profiles/fdb_v3_config.py`) and document the exact submission config in README.

### [CRITICAL] FDB-v3 text-replay strict pass rate 21% — G4 gap suppresses score
- **Location**: `scripts/fdb_v3/run_text_replay.py`, `src/prism_rt/kernel/commit.py` (G4), `src/prism_rt/adapters/fdb_manifest.py`
- **What happens**: Day 1 FDB-v3 run (currentStatus.md lines 389-390): "Full 100-scenario T3 run... strict pass rate 21.0% (21/100)... understood to be suppressed mainly by the G4 gap above... Day 2's commit-intent policy decision is expected to close most of this gap."
- **Why it is a bug/risk**: FDB-v3 tools declare no mutability → all default to STATE_CHANGING → CommitGate G4 requires explicit `commit_intent=true` for every call including reads like `search_flights`. The Interpreter doesn't set this for reads. Result: calls sit PROPOSED forever, zero tool calls, zero score.
- **Trigger/path**: Any FDB-v3 scenario with undeclared-mutability tools.
- **Evidence from code**: `CommitGate.evaluate()` lines 136-148; `fdb_manifest.py` line 16 ("Mutability is left undeclared... ToolCatalog's safe default (STATE_CHANGING, W5) applies"); currentStatus.md lines 387-388.
- **Likely benchmark/submission impact**: Round 1 score = 0.6 × FDB-v3 pass rate. At 21%, this component alone yields ~12.6% of 60% = 7.56% of total score. With G4 fix (Day 2), expected ~40% → 24% of total.
- **Confidence**: 100% — directly measured and documented.
- **Recommended fix direction**: Enable `g4_exempt_undeclared_mutability=True` in the FDB-v3 profile (already implemented as a flag, just not defaulted on). This is the Day 2 WP1 fix explicitly deferred in currentStatus.md.

### [CRITICAL] LiveKit voice path: CUDA OOM risk on evaluator GPU; model downloads at runtime
- **Location**: `docker/fdb_v3/Dockerfile`, `src/prism_rt/voice/agent.py`, `src/prism_rt/voice/speech.py`
- **What happens**: 
  - Dockerfile uses `nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04` (organizers: 48GB GPU, CUDA 12.x/13.x)
  - Whisper (faster-whisper-large-v3-turbo) + Kokoro-82M + Parakeet (FDB scorer) = ~3 models on GPU
  - Dev laptop (8GB) OOMs; `JANUS_WHISPER_COMPUTE=int8_float16` workaround used locally
  - Models downloaded at container start via `snapshot_download()` (Hugging Face) — not baked into image
- **Why it is a bug/risk**: 
  - Evaluator environment may have different GPU memory, CUDA version, or network access
  - `snapshot_download` at runtime = non-reproducible, potential failures, network dependency
  - `_SHARED` global dict in `agent.py` (line 119) loads models per process; with `num_idle_processes=1` default, two copies load (active + prewarmed)
  - `JANUS_JOB_EXECUTOR=thread` shares one copy but "produced client aborts and silent output in later jobs" (line 117)
- **Trigger/path**: LiveKit worker start (`python -m prism_rt.voice.agent start`)
- **Evidence from code**: `agent.py` lines 112-118, 133-134, 143-144; `speech.py` lines 68-79, 194-208; Dockerfile lines 70-73, 89-90.
- **Likely benchmark/submission impact**: Voice path (30% of scenarios) may fail to start or OOM during evaluation. Non-reproducible model downloads violate "one-command reproduction" requirement.
- **Confidence**: 90% — dev environment confirmed OOM; evaluator GPU is 48GB (6x dev) but concurrent Parakeet scorer adds pressure.
- **Recommended fix direction**: Bake model weights into Docker image (or use pre-warmed volume `janus_invest_hf` reliably); test on 48GB GPU; consider `thread` executor with fixes for the "client aborts" issue.

### [HIGH] One-command reproduction depends on external FDB checkout and data

- **Trigger/path**: `docker run` for FDB-v3 voice evaluation.
- **Evidence from code**: `dev_livekit_run.sh` lines 21-22, 70-71; Dockerfile lines 97-99; `fetch_fdb.sh` (not fully read but referenced).
- **Likely benchmark/submission impact**: Reproduction failure → 0% on 60% FDB-v3 component.
- **Confidence**: 95% — explicitly documented as external dependency.

### [HIGH] Write-lineage livelock (v10-3 fix) — honest failure but no retry path
- **Location**: `src/prism_rt/kernel/executor.py` lines 192-204, 390-396, 806-837
- **What happens**: A corrected WRITE (different fingerprint) proposed before original's result arrives; original confirms anyway (`COMPLETED_AFTER_CANCEL`); corrected write blocked forever by G6 (same lineage, different fingerprint). Fix: `_fail_goal` with honest message "a previous X request already went through before I could change it".
- **Why it is a bug/risk**: The architecture doc (§8.8) describes a "modify" tool or interactive CLARIFY as the intended resolution — neither exists. The fix is an honest failure, which is safe but means the user's correction is not fulfilled. In a travel booking scenario, "actually the 8pm flight" → agent says "I couldn't complete this — a previous book_flight request already went through."
- **Trigger/path**: Correction during in-flight write whose original result arrives late.
- **Evidence from code**: `executor.py` lines 806-837 docstring quotes §8.8 worked example; `tests/test_write_lineage_regression.py` exists.
- **Likely benchmark/submission impact**: Functional correctness (no double-booking, no false completion) but user experience gap. May affect "use-case extension" 20% score if the extension demonstrates correction handling.
- **Confidence**: 95% — fix verified, but design limitation acknowledged.
- **Recommended fix direction**: Document as known limitation; consider adding a "modify" tool pattern for the extension demo.

## Race / Concurrency Findings

### [HIGH] TRIAGE hold + speculative interpretation interaction (fixed in M4)
- **Location**: `src/prism_rt/kernel/task.py` lines 71-72, 253-267; `src/prism_rt/kernel/interpret_apply.py` lines 257-269
- **What happens**: Speculative INTERPRET runs on turn prefix while user speaks. If a correction arrives, the speculative job's read set (excludes `pending_interpretation_turn`) must not self-invalidate. The queue (`enqueue_interpretation`) orders turns strictly.
- **Status**: Fixed in currentStatus.md "M4 built" section (lines 300-309). Explorer found 126/471 failing schedules → 0/9,142 after fixes. Three bugs fixed: TRIAGE hold never built, rapid follow-up erasure, stuck speculative correction.
- **Confidence**: 95% — verified by bounded exploration (9,142 schedules clean).

### [HIGH] ASR capture-order release + dedupe window (fixed in M4 multimodal)
- **Location**: `src/prism_rt/kernel/audio.py` lines 124-171, 192-220
- **What happens**: Transcripts released in completion order → earlier failed clip retried and applied after later clip → "Find flights to Pune" after "actually Mumbai". Fix: hold transcripts, release strictly in capture order, AUTO mode dedupe window (800ms) discards ASR if text covers window.
- **Status**: Fixed in M4 multimodal coverage (currentStatus.md lines 311-330). 12 bugs found and fixed via explorer.
- **Confidence**: 95% — 17,336 schedules clean after fixes.

### [MEDIUM] Speculative interpretation cache + EOT promotion race
- **Location**: `src/prism_rt/kernel/task.py` lines 240-267; `src/prism_rt/kernel/turns.py` lines 203-232, 265-281
- **What happens**: At EOT, if cached speculative result's digest matches final prefix → apply in same step (0µs TTFS). If running job matches → wait for it. If stale cache → fallback to non-speculative dispatch.
- **Risk**: A growing prefix makes completed job's digest stale → redispatched against latest prefix. The "coalescing" logic (line 259-260) returns early if job running, but the running job's read set may become invalid before it completes. This is handled by K4 (read-set check at result application).
- **Status**: Tested in `test_phase6.py` (8 tests). Measured 300,000µs → 0µs TTFS on T-06 scenario.
- **Confidence**: 90% — logic sound, but live model latency variance could cause edge cases.

## CommitGate / State Integrity Findings

### [HIGH] G6 lineage check blocks corrected writes permanently (v10-3 fix)
- **Location**: `src/prism_rt/kernel/commit.py` lines 155-162; `src/prism_rt/kernel/executor.py` lines 806-837
- **What happens**: G6 blocks any future write to a plan step once ANY effect confirms for that lineage — no distinction between same-fingerprint retry (correct) and different-fingerprint correction (incorrect). Fix in `executor._write_lineage_confirmed_elsewhere()` detects different-fingerprint CONFIRMED effect and fails honestly.
- **Why it matters**: Without fix, corrected write sits PROPOSED forever (same livelock class as S-07).
- **Status**: Fixed and regression-tested (`test_write_lineage_regression.py`).

### [HIGH] CANCEL_REQUESTED calls blocked replacement until late result resolved (fixed)
- **Location**: `src/prism_rt/kernel/executor.py` lines 312-317; currentStatus.md line 167
- **What happens**: A cancelled call's late result formally resolved it (~800ms later), blocking the replacement's proposal. Fix: CANCEL_REQUESTED gets immediate fresh attempt, uncounted against retry limits.
- **Status**: Fixed in V2 test-writing phase.

### [MEDIUM] CommitGate G9 (read-set valid at emission) enforced by EmissionGate, not CommitGate
- **Location**: `src/prism_rt/kernel/commit.py` lines 9-10 (docstring); `src/prism_rt/kernel/emission.py` line 135
- **What happens**: CommitGate.evaluate() only checks read-set at DECIDE phase. EmissionGate._validate() re-checks at EMIT phase (G9). This is correct architecture — but means a read set could become invalid between DECIDE and EMIT in the same step (no async in between, so only if another component in same step mutates state).
- **Risk**: Very low — kernel step is synchronous, DECIDE→EMIT are sequential phases with no mutation between them except what DECIDE itself schedules.

### [LOW] EffectLedger.by_lineage overwrites on fingerprint match (line 145-146)
- **Location**: `src/prism_rt/store/ledgers.py` lines 145-146
- **What happens**: `set_status` updates `_by_lineage` only if the lineage's current fingerprint matches. If a different-fingerprint effect exists for same lineage (corrected write), the lineage map points to the old one. This is intentional — G6 checks `by_lineage` and compares fingerprint.
- **Status**: Correct for the v10-3 fix design.

## Things That Look Correct

1. **Single-writer kernel step** — `Kernel.step()` is synchronous, all mutation inside `StoreTxn` context manager, `MutationGuard` enforces. No async in kernel. ✓

2. **Seven-phase step order** — ORDER, APPLY, INVALIDATE, DECIDE, EMIT, COMMIT, DISPATCH, LOG. Fixed order in `step.py` lines 109-179. DECIDE sub-order: cancellation, TaskStateMachine, Perception, ASR, Frame, PlanExecutor, CommitGate, FastResponder. ✓

3. **Optimistic concurrency via read-sets** — `FactStore.is_valid()` checks existence, non-retracted, digest match. Version not compared (allows revert). `build_read_set()` captures (key, ver, digest). ✓

4. **Same-step cancellation** — `InvalidationEngine.invalidate()` called in INVALIDATE phase (step.py line 134), marks calls INVALIDATED/DISCARDED, `cancellation_actions()` emits CANCEL in DECIDE phase before other emissions. ✓

5. **READ vs WRITE separation** — CommitGate G1-G3,G8 for all calls; G3-G7,G10,G11 write-only. EffectLedger created for WRITE at admission (commit.py line 219-228). ✓

6. **CommitGate G5/G6/G7 duplicate prevention** — by_fingerprint (G5), by_lineage (G6), UNKNOWN effect (G7). EffectRecord created at admission (PENDING), updated to CONFIRMED/FAILED/UNKNOWN at result. ✓

7. **Emission order** — CANCEL → SPEAK → TOOL_CALL → CLARIFY → FINAL (emission.py line 40-46). ✓
