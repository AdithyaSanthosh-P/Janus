# Independent Review Findings — 2026-09-19

## Summary
Building on the Opus and Sonnet reviews, I focused heavily on the "who sets this flag" pattern across `GoalStatus`, `TaskState`, `CallStatus`, and `EffectStatus`. This investigation uncovered two significant bugs related to how stale or abandoned state-changing (WRITE) calls are handled and reported when they successfully execute against the tool provider despite being cancelled.

---

### Finding 1: W4 Violation (No reconciliation for STALE/RETAINED writes)
**Severity:** MEDIUM
**Confidence:** HIGH

**Location:**
- `src/prism_rt/kernel/results.py`: Lines 92-100 (Branches 5 and 6)
- `src/prism_rt/kernel/responder.py`: Lines 282-314 (`_reconcile_completed_after_cancel`)

**Description:**
The W4 core invariant guarantees "no false undo claims" — meaning that if a state-changing tool call executes successfully against the provider, the user MUST be informed, even if the system cancelled or abandoned it. 
In `results.py`, if a tool result arrives and its goal is no longer active (Branch 5) or its read set is invalid (Branch 6), the effect is correctly settled as `EffectStatus.CONFIRMED`. However, the call's status becomes `CallStatus.RETAINED` or `CallStatus.STALE`.
In `responder.py`, the reconciliation notice check (`_reconcile_completed_after_cancel`) *only* covers `CallStatus.COMPLETED_AFTER_CANCEL`. It entirely ignores `RETAINED` and `STALE` calls. As a result, if a write successfully executes but was marked `RETAINED` or `STALE`, its effect is permanently dropped without notifying the user, violating W4.

**Why this was hidden:**
Because `InvalidationEngine` proactively emits `CANCEL` actions for invalid read sets in the same step they change, most stale calls become `CANCEL_REQUESTED` and hit Branch 4 instead of Branch 6, correctly triggering reconciliation. However, the theoretical gap remains for any path that reaches Branch 5 or 6 (e.g., if a tool provider ignores the cancellation request or if the result is in-flight simultaneously).

### Finding 2: False `EFFECT_DONE` claim for successfully cancelled/stale writes
**Severity:** HIGH
**Confidence:** HIGH

**Location:**
- `src/prism_rt/kernel/responder.py`: Lines 206-219 (`_has_confirmed_write`)
- `src/prism_rt/store/ledgers.py`: Line 85 (`latest_by_step`)

**Description:**
When emitting a `FINAL` action, `responder.py` assigns `claim_grade=ClaimGrade.EFFECT_DONE` if `_has_confirmed_write` returns True. `_has_confirmed_write` calls `store.call_ledger.latest_by_step` to find the most recent call for a WRITE step, and checks if its effect is `CONFIRMED`.
Crucially, `latest_by_step` returns the last call *regardless of its status*. If the latest call for a write step was cancelled (e.g., due to a read-set invalidation) but its tool result came back `ok` (which legitimately makes its effect `CONFIRMED`), `_has_confirmed_write` will return `True`. 
This causes the final utterance for the goal to falsely claim `EFFECT_DONE` based on a stale/cancelled write that wasn't actually part of the final successful plan.

**Repro / Proof:**
Added `test_w4_stale_write_reconciliation` in `reviews/sonnet/pass2_semantic.py` (TEST-13).
