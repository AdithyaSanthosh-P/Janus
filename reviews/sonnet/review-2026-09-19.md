## Findings

### F-SONNET-1 — Latent bug: `task.py` RESPONDING state re-dispatch check uses `is None` instead of `is None or status == RETRACTED`
**Severity:** Low (untriggered in current code paths)  
**Confidence:** High  
**File:Line:** `src/prism_rt/kernel/task.py:86`

```python
# Line 78 (EXECUTING → RESPONDING transition): correctly handles both cases
if pending_text is None or pending_text.status == FactStatus.RETRACTED:

# Line 86 (RESPONDING recovery): only checks None, misses RETRACTED
if pending_text is None and not store.jobs.running_by_kind_goal(JobKind.COMPOSE, gid):
```

**What's wrong:** `store.facts.get()` returns a `Fact` object even for retracted facts — it returns the object with `status == RETRACTED`, not `None`. So `pending_text is None` is `False` for a retracted fact. If `compose.{gid}.text` becomes RETRACTED while the goal is in `RESPONDING` state, the recovery path (line 86) silently fails to re-dispatch COMPOSE, leaving the goal stuck in `RESPONDING` forever.

**Why untriggered today:** `compose.{gid}.text` is only ever retracted by `emission.py._complete_goal()` (line 170), which runs as an emission side-effect _after_ a successful FINAL emit — by which point the goal transitions to COMPLETED and never re-enters RESPONDING. No current code path sets a COMMITTED `compose.{gid}.text` and then retracts it while the goal is still in RESPONDING.

**Risk:** Any future change that retracts `compose.{gid}.text` before FINAL emission (e.g. a frame rollback path, a watchdog + recovery sequence, or a second correction arriving in the same step as RESPONDING is entered) would trigger a silent livelock. The EXECUTING→RESPONDING check at line 78 handles it correctly; line 86 does not — an inconsistency that will eventually bite.

**Repro (structural — no triggering path today):**
```python
# From task.py audit (TEST-11 in pass2_semantic.py):
# Line 86 check: `pending_text is None` 
# RETRACTED fact: pending_text = Fact(..., status=RETRACTED)  → not None
# Condition: False → COMPOSE never re-dispatched → goal stuck in RESPONDING
```

**Recommended fix:**
```python
# Line 86
if (pending_text is None or pending_text.status == FactStatus.RETRACTED) \
        and not store.jobs.running_by_kind_goal(JobKind.COMPOSE, gid):
```
This matches the guard already used at line 78 identically.

### F-SONNET-2 — S-07 (unseen tool): goal silently livelocks in EXECUTING state indefinitely
**Severity:** Medium  
**Confidence:** High  
**File:Line:** `src/prism_rt/kernel/executor.py:136-150` and `src/prism_rt/kernel/commit.py:40-43`

**What's wrong:** When the Planner returns a plan referencing a tool not in the current manifest, `PlanExecutor.propose_ready_calls()` creates a `CallRecord` with `status=PROPOSED` for that tool unconditionally. Every step, `CommitGate.scan_and_admit()` evaluates this call and returns `GateDecision(allowed=False, rule_id="G1")` (tool not usable). But CommitGate does NOT change the call's status — it stays `PROPOSED` indefinitely. No code path transitions a G1-blocked `PROPOSED` call to `FAILED`, so `PlanExecutor._fail_goal()` is never invoked. The goal stays `EXECUTING` forever.

**Repro (verified in TEST-6):**
```python
# Manifest: search_flights only
# Plan from provider: step s1 with tool="nonexistent_magic_tool"
# After 3 seconds: goal.status=GoalStatus.ACTIVE, goal.task_state=TaskState.EXECUTING
# call c-0001: status=PROPOSED, blocked by G1 every step
# No CLARIFY, no FINAL, no failure — pure livelock
```

**Confirmed by `reviews/sonnet/pass2_semantic.py` TEST-6:** goal is `GoalStatus.ACTIVE, TaskState.EXECUTING` after 3 seconds of draining.

**Note:** This is listed as an untested scenario in `currentStatus.md` ("S-07 — named in the public suite"), so the team is aware the scenario has no test. The livelock is the concrete behavioral consequence.

**Recommended mitigation:** In `CommitGate.scan_and_admit()`, when a call is permanently blocked (G1: tool doesn't exist and can't become usable unless the manifest changes), either (a) mark the call `FAILED` directly so `PlanExecutor` can count it against `max_retries` and invoke `_fail_goal`, or (b) add a G1-specific check in `PlanExecutor.propose_ready_calls()` before creating the CallRecord.

### F-SONNET-3 — TraceChecker P3 check uses `invalidated_call_ids` but does not verify CANCEL emission ordering
**Severity:** Low (documentation gap, not a kernel correctness bug)  
**Confidence:** High  
**File:Line:** `src/prism_rt/sim/checker.py:46-63`

**What's checked:** "Every call invalidated this step has a CANCEL emitted this same step." This correctly catches the case where invalidation fires but no CANCEL goes out.

**What's NOT checked:** Whether the CANCEL was emitted *in the same action batch step* that the invalidating fact changed, or whether it might have slipped to the next step (e.g. if EmissionGate rejected it and it was re-attempted in the next step). The checker iterates `report.emit_report.emitted` (the same-step emissions) against `report.invalidation.invalidated_call_ids` — so it does check same-step; this is correct.

**The subtle gap:** The `_validate` method in `emission.py` can reject a CANCEL if `target.status in TERMINAL_CALL_STATUSES or target.status == CallStatus.CANCEL_REQUESTED`. If the CANCEL is rejected by EmissionGate (e.g. because it was a duplicate), P3 would still fire a violation — even though the cancellation was already effective. In practice, the `InvalidationEngine.cancellation_actions()` only generates a CANCEL for calls whose current status would not be rejected (it checks the ledger first), so this is not a real false-positive path today. Still worth noting for future P3 hardening.

### F-SONNET-4 — FRAME job read set excludes the `result.<call_id>` of already-consumed upstream steps in multi-step plans
**Severity:** Low (behaves correctly; structurally not a completeness bug)  
**Confidence:** High  
**File:Line:** `src/prism_rt/kernel/frames.py:179`

```python
read_keys = ["goal.active", "catalog.version"] + [f"slot.{gid}.{name}" for name in facts]
```

**What's not in FRAME's read set:** `result.<call_id>` for consumed upstream steps (not the pending step — the ones that already completed). 

**Why this is actually correct:** `_pending_step()` returns a step only when exactly one step is not yet consumed-and-valid. For that last step (the one being framed), its result doesn't exist yet (it's IN_FLIGHT). For the already-consumed steps, their result facts are immutable once written (`result.*` keys are only written once by `results.py`, never retracted). A correction that invalidates an upstream step would also invalidate that step's read_set, making it no longer "consumed-and-valid" — so `_pending_step()` would return `None` and the FRAME dispatch would be suppressed entirely. The frame's slot keys already capture the slot dependencies.

**Verdict:** Correct as implemented. Not a bug. Documented here because the review prompt specifically asked about FRAME read-set completeness.

### F-SONNET-5 — Speculative interpretation cache: spec-interpret promotion bypasses `session.last_eot_ts` for the WRITE settle barrier
**Severity:** Low (verified working correctly; documented nuance)  
**Confidence:** High  
**File:Line:** `src/prism_rt/kernel/turns.py:186-196`

**Scenario examined (TEST-3):** speculative_interpretation_enabled=True, settle_barrier_enabled=True, settle_ms=200ms. Turn closes (EOT at t=200ms). Spec interpretation is promoted immediately. Goal enters PLANNING, then EXECUTING. WRITE step (book_flight) sits behind G10 (settle barrier: must wait until t≥400ms from EOT).

**Result:** Correct — the settle barrier fires correctly because `request_interpretation()` (line 153-160) sets `session.last_eot_ts = now_us` unconditionally before the speculative promotion check. `CommitGate.G10` reads that fact and computes the settle window from it. The speculative promotion path (line 187-188) runs after this fact is set. So even if spec interpretation fires immediately, `session.last_eot_ts` is already set to EOT timestamp, and the 200ms settle window is measured from that.

**Verdict:** Correct. The settle barrier and speculative interpretation compose correctly.

### F-SONNET-6 — Watchdog event requires `wall_elapsed_s` in the codec but the `reducers.py` docstring suggests testing it like any event (minor documentation/ergonomics gap)
**Severity:** Very Low (documentation / developer ergonomics)  
**Confidence:** High  
**File:Line:** `src/prism_rt/adapters/codec.py:47` and `src/prism_rt/kernel/reducers.py:202-215`

`_REQUIRED_FIELDS["watchdog"] = ("wall_elapsed_s",)` in codec.py. The `_apply_watchdog` docstring says it is "directly testable by sending this envelope like any other." This is true — but only if the test provides `wall_elapsed_s`. Sending `{"type": "watchdog", "payload": {}}` silently returns `[]` from the codec. Not a kernel bug, but a gotcha for future test writers.

**Repro (my TEST-12 initial failure):** The test sent `{"type": "watchdog", "payload": {}}` → codec decoded to `[]` → kernel never saw the event → in-flight READ stayed IN_FLIGHT.

**Fix:** Send `{"type": "watchdog", "payload": {"wall_elapsed_s": 105.0}, "ts_us": ...}`.

## Summary verdict

The kernel is robustly built and handles all tested cross-phase interactions correctly. Pass 1 (300 random seeds) produced zero crashes or invariant violations. Pass 2 (12 targeted semantic tests) produced zero behavioral bugs in the tested paths.

**Two real issues found:**
1. **F-SONNET-1 (Latent bug):** `task.py:86` RESPONDING recovery checks `is None` not `is None or RETRACTED` — inconsistent with line 78, no triggering path today, but will silently livelock if compose text is ever retracted pre-FINAL in the future. One-line fix.
2. **F-SONNET-2 (Real behavioral gap):** S-07 (unseen tool in plan) silently livelocks in EXECUTING state — the plan references a tool not in the manifest, CommitGate G1 blocks the call every step without marking it FAILED, and no recovery path fires. The goal neither completes, fails, nor clarifies — it stays EXECUTING indefinitely. Already flagged as an untested scenario; the behavioral consequence is now confirmed.

All other reviewed scenarios (FRAME read-set, C9+correction, speculative+settle, watchdog, manifest update, stale result routing, duplicate delivery, audio/text) are correct.
