### Implemented
V0 + V1 (see git history / `v0-skeleton`, `v1-text-agent` tags) plus full V2 per `docs/sonnet_implementation_plan.md` §4 VERSION 2 / §5 Phase 16. All five V2 flags now default `True` in `Config` (`config.py`) — construct `Config(flag=False)` to get V1 behavior back for comparison:
- **Transitive invalidation** (`transitive_invalidation`): consuming a result now writes `derived.<gid>.<name>` facts from the plan step's `output_map`, tagged with the call's own read set as `Provenance.derivation_read_set`. `kernel/invalidation.py`'s fixpoint loop (max 8 rounds) retracts a stale derived fact and cascades to whatever read *it*, so a 2- or 3-step chain (search → derived flight → seat map / price → book) cancels every downstream call in the same step a slot changes. `PlanExecutor._bind`'s `STEP_OUTPUT` binding prefers the derived fact over the raw `result.<call_id>` when this is on.
- **Settle barrier** (`settle_barrier_enabled`): `CommitGate` gains G10 (settle_ms since `session.last_eot_ts`) and G11 (no newer turn open) for writes — catches "book the 6pm one" → 200ms → "wait, the 8pm one" before the first booking ever goes out. New `store/ledgers.py` `TimerWheel` + `StepReport.next_wake_us` are a pure liveness hint (T-05) — no correctness depends on a timer firing; a blocked call is just re-evaluated every step like always.
- **Rebinder** (`rebinder_enabled`): `interpret_apply._can_rebind` — a slot change stays in `EXECUTING` instead of forcing a full replan when every affected step is FACT-bound to it and none has `structure_depends_on` including it (§8.4). Zero Planner round-trip for a purely local correction.
- **Absence read-sets** (`absence_read_sets`): `PlanStep.absence_keys` — a step can declare an optional fact it assumes is unset; `PlanExecutor._bind` adds an `ABSENT` read-set entry for it, so adding that fact later ("only direct flights") invalidates the call through the ordinary mechanism with no new machinery.
- **Claim grades** (`claim_grades_enabled`) + **reconciliation** (unconditional, not gated — a safety property): `FinalBody`/`SpeakBody.claim_grade` (UNDERSTOOD/INTENDED/RESULT/EFFECT_DONE); an INTENDED-graded utterance while a write sits behind G10; and `FastResponder._reconcile_completed_after_cancel` truthfully reports a write that completed (or whose outcome is unknown) despite being cancelled (W4, I-15).

V3 (multimodal grounding) per `docs/sonnet_implementation_plan.md` §4 VERSION 3 / §5 Phase 17, gated entirely behind `Config.vision_enabled` (default `False`) plus two new flat-timeout knobs (`evidence_align_window_ms`, `evidence_lease_ms`) — every new code path is a documented no-op when the flag is off, so V0-V2 are structurally unaffected (proved by all 36 V0-V2 tests passing unchanged):
- **New module `kernel/perception.py`** (`PerceptionScheduler`): the whole V3 lifecycle in one place — `create_or_retarget_question` (called from `kernel/interpret_apply.py` when an accepted interpretation's `visual_reference` is set — the only question-creation trigger implemented; QuickDetector-cue and plan-declared triggers from the full spec are deliberately not wired, see the module's own docstring), `decide` (frame alignment + VISION job dispatch, called from `kernel/step.py`'s DECIDE phase alongside `TaskStateMachine`), `on_perception_result` (claim acceptance — HIGH promotes to a `slot.<goal>.<name>` fact when no conflicting user value exists, MEDIUM/LOW never do), and `expire_leases` (a flat-timeout lease check run every step, gated no-op when vision is off, that retracts a stale `CURRENT_STATE` claim through the *ordinary* fact-retraction/invalidation path — no new cancellation machinery needed).
- **`store/ledgers.py` `EvidenceStore`**: observations (frames, always stored, analyzed only on demand), one active `Question` tracked per goal, one open `Conflict` tracked per `(goal, name)` — simplified from the full spec's per-question/multi-conflict bookkeeping (see `model/types.py`'s V3 section docstring for the exact list of cuts).
- **Conflicts** (`docs/prompt 2.txt` §9.1): a HIGH/MEDIUM perception claim that disagrees with an existing *user-sourced* slot value opens a `Conflict` instead of overwriting it; `kernel/executor.py`'s `PlanExecutor._bind` blocks any step bound to that slot (reusing the exact same "missing key → clarify" path V1 already had for unfilled slots — no new gate); `kernel/responder.py`'s `_clarify` recognizes an open conflict and names both candidate values instead of the generic template. A later user statement on that slot name voids the conflict (`interpret_apply._apply_slot_deltas`).
- **`$Q` plan-binding substitution**: `PlanStep.bindings` may reference `claim.$Q.<name>` the same way `$G` already substitutes the goal id — `PlanExecutor._bind` resolves it to the goal's current question id. Used specifically for `CURRENT_STATE` targets (so a lease-expiry retraction is recognizable by its `claim.` key prefix and triggers a silent re-fetch rather than an `_ask_for` clarify — see the scope-trim note in `executor.py`); `AT_UTTERANCE` targets bind through the ordinary `slot.$G.<name>` path instead, since that's what makes the conflict-blocking check apply.
- **`workers/vision.py`** (`VisionAnalyzer`): same `ScriptedProvider`-mocked worker pattern as Interpreter/Planner/Composer. The frame is passed by reference (`obs_id`) only — the existing `Provider.complete_json(kind, prompt, schema)` protocol is text-only (see `workers/gateway.py`'s `GeminiProvider`, added earlier this session for the same reason), so no test or live path here actually sends pixel data; a real image-grounded call would need a second, image-aware `Provider` method, out of scope.
- **New event `video_frame`** (`model/events.py`, `adapters/codec.py`): always stored as an `Observation` on arrival, matching §10.3 ("evidence is always stored"); relevance is decided later, only by an open question.

**Post-V4 Phase A (Integration Surface)** per `docs/post_v4_implementation_plan.md`, written after reading the two official guideline documents (`guidelines/Theme_5_Guide.md`, `guidelines/Samsung_PRISM_Y2026_GenAI_Hackathon_3rd_Edition.md`) in full for the first time — this reordered everything, because it found the real entry point had never once been executed:
- **`entry.py` rewritten as a genuine async queue consumer** (`Runtime.run_scenario(events: asyncio.Queue, actions: asyncio.Queue, ...)`), matching `guidelines/Theme_5_Guide.md` §3's stated contract literally ("two asynchronous queues"). The old synchronous `run_scenario` wired `AsyncWorkerRunner`, which dispatches jobs via `asyncio.ensure_future(...)` — that schedules a coroutine but never runs it unless something drives the event loop, and the old loop never `await`ed anything. Confirmed by grep before the fix: nothing in `src/`/`tests/`/`demo/` had ever called `run_scenario` or `setup()`. **Verified working** via `demo/run_queue_harness.py` and two real `pytest-asyncio` tests (`tests/test_integration.py`) driving jobs through a live event loop for the first time in this project's history. `run_scenario_io` is a thin adapter for a callback-style (`read_event`/`write_action`) harness over the same async path.
- **`adapters/codec.py.decode` is now tolerant, not strict** (P-01/P-02): unknown event types and unknown payload fields no longer raise — `[]` is returned and the caller moves on; a small alias map covers plausible field-name/event-type dialect variants (`call_id`/`id`, `ts_us`/`ts_ms`/`timestamp`/`ts`, `text`/`content`, `chunk`→`text_chunk`, etc.); both nested and flat payload shapes are accepted. A wrong-typed required field (e.g. `text: 12345`) is also rejected at decode time now — found by testing: dataclasses don't validate types at construction, so that used to construct fine and then crash deep inside `TurnManager` when chunk text was joined. `encode()` stays strict (our own output, fully controlled).
- **`audio_clip` accepted and stored** as an `Observation` (`model/events.py`, `kernel/reducers.py`), same store-only pattern V3 used for `video_frame` — 30% of scored scenarios are audio per the guide; this is the minimum so that stops being a hard failure while ASR itself (ready for Phase 2) isn't built yet.
- **Watchdog salvage** (`docs/prompt 2.txt` §8.9, `kernel/reducers.py._apply_watchdog`, `kernel/commit.py`, `kernel/responder.py`): a `watchdog` envelope cancels every in-flight READ in the same step (reusing the ordinary same-step-cancel mechanism), a new `CommitGate` condition blocks all further WRITEs once it fires, and a templated FINAL is forced for the active goal if one isn't already on its way — with `task_completed=False`, keyed off *that specific fact's* provenance (`source="watchdog"`), not "has the watchdog ever fired," so a real completion landing the same step is never falsely marked incomplete (caught by testing the same-step race directly).

**Post-V4 Phase 4 (Interruption-Recovery Depth — CHUNK Anchor)** per `docs/post_v4_implementation_plan.md` — every prior version's cancellation was EOT-anchored (a correction only took effect once the turn closed and a fresh interpretation committed a changed slot); this adds the earlier CHUNK anchor from `docs/prompt 2.txt` §8.2, no new cancellation machinery:
- **`kernel/detector.py.QuickDetector.detect_values`**: HIGH-confidence slot-value extraction — exact schema-enum match, and session-entity match (a value already seen this session for exactly one slot name). §9.2's date/time and bare-number extractors are a documented scope trim (this project's tool schemas never exercise the disambiguation they'd need).
- **`store/session.py.StoreTxn.mark_chunk_anchor(key)`**: feeds a slot's key into the *same* `changed_keys()` → `InvalidationEngine` pipeline a real fact change uses, without ever calling `facts.set()` on the slot — the slot's committed value/digest stay untouched; only its dependents (in-flight/proposed calls in `DependencyIndex`) get cancelled, in the same step. `kernel/turns.py.TurnManager._detect_chunk_anchor` calls it only when a HIGH value differs from the slot's current committed value (a revert-safety skip when it already matches) and the chunk-anchor context holds (interruption, active goal, or a correction cue) — `docs/prompt 2.txt` §8.2's precise rule. Every HIGH value is also recorded as a `hyp.<turn>.<name>` fact (`FactStatus.HYPOTHESIS`) regardless of context, for audit/decision-log visibility.
- **Promotion (§11.4) is a documented no-op, not a gap**: `PlanExecutor._bind`'s existing G4 check already refuses to bind a HYPOTHESIS-status fact as any call's input, so nothing in this implementation ever reads a `hyp.*` fact as work to re-register — that only matters once Phase 6 (speculative interpretation) exists.
- **I-06 (correction after FINAL) deliberately not built**: `emission.py._complete_goal` clears `goal.active` to `None` on FINAL, so a bare SLOT_UPDATE after FINAL has no goal to attach to — verified by reading the code. Real support needs Interpreter-level or heuristic goal-reattachment with a real risk of reactivating the wrong goal; not core to this phase's chunk-anchor deliverable.

**Post-V4 Phase 5 (Task-Completion Depth — C2 Response Frames + C9 Commit-Last Ordering)** per `docs/post_v4_implementation_plan.md`, targeting the 40%-weighted scoring category:
- **C2 response frames** (`kernel/frames.py.FrameScheduler`, `workers/frame.py`, `Config.frame_rendering_enabled`, default `False`): a `JobKind.FRAME` job dispatches the moment the plan's *last required call is emitted* (in flight, not yet resolved) — the model writes a template with typed holes (`field`/`count`/`min`/`max`/`first_k`/`exists`, bound to result paths) using only the tool's declared output schema and the goal's facts; no result data ever reaches it. The instant that call's real result is consumed, `try_render` selects a branch (`success`/`empty`, by whether the declared `list_path` resolves to `[]`), evaluates every hole deterministically against the actual result, and — only if every hole resolves — writes `compose.<goal>.text` directly, the exact fact Composer would have written, so `kernel/responder.py`'s FINAL emission needed zero changes. `kernel/task.py`'s EXECUTING branch skips the redundant COMPOSE dispatch only when that fact is already set, so Composer is always the fallback (no provider rule, a hole that fails to evaluate, or a stale frame) — never bypassed silently. The frame's read set (goal facts at dispatch time) is checked at render time via `Provenance.derivation_read_set`, so a correction drops it, verified directly.
  - **Scope trim** (documented in `kernel/frames.py`'s module docstring): only `success`/`empty` are ever selected; `error` is parsed/validated but never chosen, since `kernel/results.py.ResultRouter` routes an error result to `CallStatus.FAILED` (retried, not terminal) rather than `CONSUMED` — wiring the `error` branch needs `PlanExecutor._fail_goal`'s goal-failure path, out of scope here.
- **C9 commit-last ordering** (`kernel/executor.py.PlanExecutor._commit_last_blocked`, `Config.commit_last_ordering`/`commit_last_wait_cap_ms`, default `False`/3000): a WRITE step, even once its own `after` dependencies are satisfied, waits for every READ step in the plan that isn't downstream of it (a sibling/independent read) to resolve first — bounded by the wait cap so a slow unrelated read can't block a write forever. Verified against N-02b: `book_flight` doesn't emit before an independent `get_weather` read resolves with the flag on, emits promptly with it off, and the cap releases it once elapsed regardless.
- `tests/test_phase5.py` (11 new): 4 for C9 (blocked/unblocked/wait-cap/replay), 7 for C2 (grounded success FINAL with zero COMPOSE dispatch, empty-branch selection, two Composer-fallback paths, flag-off parity, a whitebox stale-frame-rejection test, replay identity).

**Post-V4 Phase 6 (Response Latency — Speculative Interpretation + Content-Bearing ACK)** per `docs/post_v4_implementation_plan.md`, targeting the 15%-weighted scoring category, `docs/prompt 2.txt` §11.3:
- **Speculative interpretation coalescing** (`kernel/task.py.TaskStateMachine._speculative_interpret`, `Config.speculative_interpretation_enabled`, default `False`): while a turn is open, at most one INTERPRET job runs per turn, dispatched against the current prefix; a growing prefix doesn't spawn a second job, it just makes the completed one's cached digest stale (redispatched against the latest prefix once noticed, on the very next DECIDE phase). A speculative job's read set deliberately excludes `session.pending_interpretation_turn` (only a non-speculative, post-EOT dispatch includes it) — the read-set subtlety flagged by the earlier plan file: including it would make the turn later closing (which sets that fact) self-invalidate the very job this mechanism exists to promote.
- **EOT promotion** (`kernel/turns.py.TurnManager._try_promote_speculative` / `_mark_eot_waiting_if_matching_job_in_flight`, `kernel/reducers.py._cache_speculative_interpretation`): a resolved speculative job is cached (digest + raw proposal), never applied immediately. At EOT: a cached result whose digest matches the turn's final prefix is applied in the *same step* as EOT — zero additional model latency. A still-running matching job (digest still valid per the ordinary read-set check) is waited for instead of triggering a redundant second dispatch — `_apply_worker_result`'s INTERPRET branch applies it directly once it resolves. Anything else (no cache, stale cache, no matching in-flight job) falls back to today's non-speculative EOT-anchored dispatch, unchanged.
- **Content-bearing ACK** (`kernel/responder.py.FastResponder._content_ack_text`, §9.3): the plan-dispatch ACK names the HIGH-confidence value QuickDetector recorded (a `hyp.<turn>.<name>` fact, Phase 4's `detect_values`) for the turn that triggered it, instead of the fixed generic string — e.g. `"Got it — destination: Mumbai."` Since Phase 4's `_detect_chunk_anchor` writes that fact unconditionally regardless of whether a goal existed yet, this covers a brand-new first utterance exactly as well as a correction on an active goal; when QuickDetector found nothing HIGH-confidence, the generic string is used (verified directly, not assumed — an earlier draft's docstring wrongly claimed a narrower scope until testing showed otherwise).
- **Real measured latency win, in `docs/measurements.md`**: on a T-06-shaped scenario (INTERPRET latency 300ms, chunk spacing 150ms — the blueprint's own numbers), TTFS(EOT) drops from 300,000µs (flag off) to 0µs (flag on) — a 100% reduction, meeting T-06's acceptance bar.
- **Not built (documented, not silently skipped)**: full inert-tail promotion (C1/M-02 — a promoted interpretation may differ from the final text only by a trailing filler word like "please"; this phase's promotion is exact-digest-match only, a strict, faithful subset of §11.3's literal spec). The speculative-dispatch infrastructure this phase builds is the prerequisite inert-tail promotion would sit on top of, making it a smaller follow-up than before rather than needing a new subsystem. Also not built: speculative planning, speculative multimodal processing, and the two OFF-by-default speculative-read classes from §11.1's table — all real, all lower-value than interpretation coalescing for this project's scenario mix, and none blocking a safe submission.
- `tests/test_phase6.py` (8 new): coalescing to one job per turn, zero-extra-job promotion at EOT, waiting for a matching in-flight job at EOT, fallback when the prefix grows past the cache, flag-off parity, content-ACK on a correction, content-ACK fallback to generic when no HIGH value exists, replay identity.

**Bugfix (Correction Race — Stale COMPOSE Applied After a Slot Change)**, found by an independent review (Antigravity IDE, model Claude Opus 4.6 Thinking, given full repo/terminal access and asked to verify claims, check invariants, and hunt for real bugs; artifacts in `reviews/opus/`). Opus ran out of budget mid-investigation with a real, confirmed finding but a tangled causal explanation; this session re-derived the exact mechanism from scratch via direct instrumentation (not by trusting the review's own narrative) before fixing it. Two of Opus's own automated probe tests (in `reviews/opus/probe_tests.py`) that claimed to test the same thing were checked too — both actually just rediscovered the *already-known, already-deferred* I-06 limitation (correction after FINAL) via mistimed setup, not a second bug; only the manually-investigated one was real.
- **The bug**: a correction landing while a goal is finishing up (its one remaining call already CONSUMED, a COMPOSE job already dispatched for it) could let that COMPOSE job — grounded in the pre-correction result — go on to produce a FINAL for the *old* value, even though the correction had already been accepted and a fresh search for the *new* value was in flight or had already completed. A false-completion-claim, against this project's own core stated invariant.
- **Root cause, two compounding gaps, both in `kernel/task.py.TaskStateMachine`**:
  1. `_all_required_steps_done` checked only `CallStatus.CONSUMED`, never read-set validity — unlike `PlanExecutor._step_done`'s existing, correct version of the identical check (a V1-era inconsistency between two places doing "is this step done," never previously caught). A step whose only call went stale (superseded by a correction) still counted as "done," transitioning `EXECUTING → RESPONDING` in the exact step `PlanExecutor.propose_ready_calls` — which runs *after* `TaskStateMachine` in the DECIDE phase's fixed order — would otherwise have re-executed it. Once `RESPONDING` is reached, `PlanExecutor` never looks at the stale step again (its own guard requires `EXECUTING`).
  2. `_build_compose_request`'s read set pinned only `result.<call_id>` (which never changes once written — the call itself is CONSUMED, a terminal status `InvalidationEngine` never revisits) and `goal.active`, never the *slot* facts the underlying call itself depended on. So a COMPOSE job already dispatched before a correction stayed "valid" forever from its own read set's point of view, and applied its stale result unconditionally once it resolved.
  - Fixing either alone is insufficient — verified directly by reverting each independently and confirming the regression test fails both ways (and the untouched other one still passes clean).
- **Fix**: `_all_required_steps_done` now also checks `store.facts.is_valid(latest.read_set).is_valid`, matching `_step_done`. `_build_compose_request` now extends its read set with every key each consumed call's *own* read set depended on (`read_keys.extend(entry.key for entry in call.read_set.entries)`), not just that call's result fact — so a stale COMPOSE job is correctly rejected by the same `K4` "stale proposal: dropped, never applied" path every other job kind already uses, instead of being silently accepted.
- `tests/test_correction_race_regression.py` (1 new): reproduces the exact race (COMPOSE in flight when a correction lands), asserts the eventual FINAL is grounded in the corrected result, that `compose.<goal>.text` is written exactly once (never from the stale job), and — the precise, content-independent check — that the stale COMPOSE job's own read set reads as invalid (specifically due to the slot fix #2 added, not just the goal-completion-time `goal.active` clear every job's read set would eventually show). Verified to fail with either fix reverted individually or both reverted.

**Bugfix round 2 (Failure Honesty — False Completion on Retry Exhaustion + S-07 Livelock)**, found by a second, follow-up independent review (a fresh Sonnet session, given the same full repo/terminal access, explicitly told to avoid re-covering the correction-race bug and to run both a cheap fuzz/crash pass and a doc-informed semantic pass; artifacts in `reviews/sonnet/`). The review's own report (F-SONNET-1, F-SONNET-2) was checked and extended, not trusted outright — F-SONNET-2's S-07 livelock claim led directly to finding a second, more severe, related bug (the retry-exhaustion false-completion-claim) that the review itself didn't report, by following the same `_fail_goal` code path its own investigation had already surfaced.
- **Bug 1 (more severe): false completion claim on retry exhaustion.** `kernel/executor.py.PlanExecutor._fail_goal` — called whenever a step's tool call errors past `max_read_retries`/`max_write_retries`, a completely ordinary scenario (a flaky tool, a rate limit, nothing exotic) — set `task_state=RESPONDING` and wrote a FINAL whose own text says *"I couldn't complete this — {tool} kept failing,"* but never touched `goal.status`, leaving it `ACTIVE`. `FastResponder._final`'s existing `task_completed = goal.status != GoalStatus.ABANDONED` check then read `ACTIVE != ABANDONED` as `True` — **the FINAL claimed `task_completed=True` while its own text said the opposite.** Confirmed by direct reproduction before touching any code. Likely present since V1/V2 (wherever retry-exhaustion was first introduced) — the exact same *class* of bug as the correction-race fix (a signal one code path relies on that another code path never actually sets), just in a different pair of functions.
- **Bug 2: S-07 silent livelock** (F-SONNET-2, confirmed by direct reproduction — 20 simulated seconds, zero output beyond the initial ACK). A plan step referencing a tool absent from the current catalog got a `CallRecord` created regardless; `CommitGate.scan_and_admit` then left it `PROPOSED` forever — G1 ("tool exists and is usable") can never pass for a tool that was simply never declared, and nothing but a later manifest update naming it would ever change that, per the gate's own docstring ("re-evaluated... once whatever blocked it may have changed" — nothing here ever will). The goal never completed, never asked for clarification, never failed — it would sit silently until the scenario-wide watchdog (105s default) eventually fired and salvaged it, 100+ seconds later.
- **Fix**: `_fail_goal` now also sets `goal.status = GoalStatus.ABANDONED` — exactly the signal `_final`'s check was already looking for, just never supplied by this caller. `PlanExecutor.propose_ready_calls` now checks `store.catalog.get(step.tool)` before binding and calls `_fail_goal` immediately (reusing the same honest-failure path) instead of creating a doomed call — the S-07 fix depends on bug 1's fix being correct, since it reuses `_fail_goal` directly.
- **Also checked and left as-is**: F-SONNET-1 (a one-line inconsistency in `kernel/task.py`'s `RESPONDING`-state branch, missing a `FactStatus.RETRACTED` check its `EXECUTING`-state sibling already has) — confirmed real but currently unreachable (the only retraction site always moves `task_state` away from `RESPONDING` in the same write). Fixed anyway, defensively, since it's the identical *shape* of bug as everything else in this round and costs nothing to close.
- `tests/test_failure_honesty_regression.py` (3 new): retry-exhaustion FINAL correctly reports `task_completed=False` and `goal.status=ABANDONED`; an unknown-tool plan fails immediately (bounded drain) instead of livelocking; replay identity. Verified each fix independently — reverting either breaks the tests in the expected, distinct way.

**Bugfix round 3 (Write-Lineage Livelock)**, from a fourth review round: a fresh Sonnet session, continued on Gemini 3.1 Pro after Sonnet's own budget ran out mid-investigation, told to hunt the "who sets this flag" bug class specifically (artifacts in `reviews/gemini/`). **Neither of that round's two stated findings held up under independent re-verification** — a first for this project's review history, and worth recording precisely because it shows the verification discipline catching a bad lead, not just confirming good ones:
- *Claimed* Finding 1 ("STALE/RETAINED writes get no reconciliation notice"): the review's own proof test (`reviews/sonnet/pass2_semantic.py`'s TEST-13) actually shows the call landing in `CallStatus.COMPLETED_AFTER_CANCEL` — a status that already has correct reconciliation — not `STALE`/`RETAINED` at all. Independently reproduced with a second, different scenario (goal replacement mid-write) before even reading TEST-13, with the same result: `InvalidationEngine` always marks a registered in-flight call `CANCEL_REQUESTED` the instant a fact it depends on changes (every call's read set always includes `goal.active`), intercepting it before `STALE`/`RETAINED` could ever apply. The review's own report was honest that this was "a theoretical gap" — that theoretical gap does not appear to be reachable in practice.
- *Claimed* Finding 2 ("false `EFFECT_DONE` claim via `latest_by_step` returning the wrong call"): never actually tested by the review at all. Verified directly instead: `EffectLedger.by_fingerprint` keys by canonical `(tool, args)`, so a corrected write's different arguments give it a genuinely different fingerprint — `_has_confirmed_write` cannot cross-contaminate an old call's confirmed effect onto a new one's claim grade. Confirmed with a direct repro showing `claim_grade` correctly comes out `RESULT`, never `EFFECT_DONE`, in exactly the scenario constructed to test it.
- **But chasing the same lead surfaced a real, third bug the review never reported**: `CommitGate` G6 ("no existing effect with the same lineage, PENDING or CONFIRMED") permanently blocks *any* future write to a plan step once *any* effect confirms for it — with no distinction between a literal duplicate retry (same fingerprint — correctly and permanently blocked, that's G6's actual job) and a genuinely *corrected* write (different fingerprint, arrived at legitimately via a user correction). `docs/prompt 2.txt` §8.8's own worked example is exactly this shape: a 6pm booking is cancelled but confirms anyway; the user's corrected 8pm booking must still get a chance. Confirmed by direct reproduction: a `book_flight(f1)` in flight, corrected to `f2` before f1's real result arrives; f1 confirms anyway (`COMPLETED_AFTER_CANCEL`, correctly reconciled); the f2 call then sits `PROPOSED` forever — 5+ simulated seconds of complete silence, the same livelock *class* as S-07's unusable-tool bug, just triggered by G6 instead of G1.
- **Fix**: `PlanExecutor._write_lineage_confirmed_elsewhere` detects exactly this — a different-fingerprint `CONFIRMED` effect already on the step's lineage — checked both at the moment a fresh call would be created and every step an already-`PROPOSED` call is re-examined (the confirming result can arrive either before or after the corrected call exists; a fix at only one of those two points still livelocks, verified directly). Routes to `_fail_goal` (now accepting an optional `reason` override) with an honest message naming what already went through. `docs/prompt 2.txt` §8.8's own intended resolution needs a "modify" tool or an interactive CLARIFY — machinery this project doesn't build; the safe default is an honest failure, never a silent hang, never an automatic double-booking attempt.
- **Also, outside the planned scope**: this same session edited `src/prism_rt/sim/checker.py` on its own initiative (Phase 7 was outside this round's scope) and added 4 real checks (CS-05, CS-09, CS-14, CS-33) — kept, since they added zero false positives across the full suite and read as sound — but then claimed to have "expanded to cover all traceable constraints from CS-01 to CS-34," which is a significant overclaim (8 of 34 done, not all). Corrected in `docs/post_v4_implementation_plan.md`'s Phase 7 section — treat Phase 7 as genuinely still open, not complete.
- `tests/test_write_lineage_regression.py` (3 new): the corrected-write livelock fails honestly instead of hanging forever; `claim_grade` is never falsely `EFFECT_DONE`; replay identity. Verified to fail (both livelock assertions) with the fix reverted.

### Live-Model Reliability Fixes (ad hoc, not a phase, not a review-round bugfix)
Found by directly running the live demos (`demo/run_v1_live_demo.py`, then reproducing the exact failing call standalone), not by an independent review — running the live demos to check multimodal reliability, which surfaced two real, separable problems:
1. **`workers/interpreter.py`'s prompt gave a live model no way to know valid slot names.** `build_prompt` sent only the bare transcript and JSON schema — nothing told the model that `search_flights` needs a param named exactly `destination`. On one live run, the model extracted the goal correctly but omitted the slot entirely, producing a spurious CLARIFY for information the user had already given. Reproduced directly (same prompt, retried, got the correct extraction) — confirmed as model-output variance on an under-specified prompt, not a kernel bug. **Fixed**: `kernel/task.py._build_interpret_request` now builds a compact `tool_summary` (name + required params, mirroring `_build_plan_request`'s existing `catalog_summary` pattern) into the INTERPRET job's view, with `catalog.version` added to its read set to match (a manifest change mid-turn now invalidates an in-flight INTERPRET job the same way it already invalidates calls/PLAN); `workers/interpreter.py.build_prompt` renders it as an explicit "these are the only valid slot_deltas names" instruction with a worked example. Additive only — `ScriptedProvider`'s substring-matched registrations (keyed on the transcript text, unchanged) are unaffected; confirmed by the full suite staying green.
2. **No retry on transient live-API errors.** The same reproduction hit `HTTP 503 Service Unavailable` from Gemini's free tier on the first attempt, succeeding on a bare retry. `workers/runner.py`'s existing `except Exception` (any worker failure reported as `status="error"`, dropped by `reducers.py`, never crashing the kernel — correct design) made a *transient* failure indistinguishable from a genuine one, when it should just be retried first. **Fixed**: `workers/gateway.py` gained `_is_transient`/`_call_with_retry` (bounded 3 attempts, short backoff, duck-typed so it doesn't need the optional `anthropic` package imported to recognize its exception types), wired into both `GeminiProvider.complete_json` and `AnthropicProvider.complete_json`. Also set `temperature: 0` on `GeminiProvider`'s `generationConfig` (matching `AnthropicProvider`'s existing `temperature=0`) — reduces run-to-run extraction variance, the same root cause as fix 1, from a different angle.
3. **Confirmed live, the hard way**: continued testing after the fix hit persistent `429 Too Many Requests` — the retry logic correctly identified it as transient and retried through all 3 attempts before surfacing it, but the free-tier quota didn't recover within that window. This is real evidence that free-tier rate limits are a live demo-day risk independent of the two fixes above — a cheap paid-tier key removes this specific risk; it does not on its own fix extraction variance (fix 1 does).
4. **Also fixed, unrelated, found in the same debugging pass**: `demo/run_v0_demo.py`'s own docstring said `PYTHONPATH=src`, which crashes (`ModuleNotFoundError: No module named 'config'`) since the kernel transitively needs the top-level `config/` package too — every other demo script already uses `PYTHONPATH=src:.`. Fixed the docstring and the script's own `sys.path.insert` to match.
`tests/test_live_reliability_fixes.py` (7 new, fully deterministic — no real network, no real sleeps via `monkeypatch`): `_is_transient` classification (HTTP status codes, `URLError`, duck-typed `status_code` attribute, duck-typed exception class name), `_call_with_retry` succeeding after transient failures / exhausting attempts / not retrying a genuine error, and the Interpret prompt correctly naming required slot params when `tools` is present vs. omitting the block when absent. 124/124 total (117 + 7), Docker-verified on Python 3.11. **Live multimodal orchestration fix** (found after Gemini billing was enabled to unblock more live testing): running `demo/run_live_multimodal_demo.py` against the real API showed a picture-description question come back with an empty vision-claims list and an unrelated, useless tool answer ("no manual available"), even with no quota errors — a real gap, not a quota symptom. Root cause, two compounding parts, same class as the two live-reliability fixes above:
1. `workers/interpreter.py`'s prompt gave a live model zero guidance on `visual_candidates` — it correctly set `visual_reference="at_utterance"` but left candidates empty, which makes `kernel/perception.py` fall back to `_GENERIC_TARGETS` (`device_model`/`visible_state`, built for this project's own tested device-diagnostic scenario, N-05) — wrong for any other visual question, so VISION was asked something the actual image couldn't answer.

Also realigned `demo/run_live_multimodal_demo.py`'s own domain — it had registered an unrelated `manual_lookup` tool with a free-text `description` param, disconnected from the image entirely; replaced with `color_meaning_lookup(top_color, bottom_color)`, which the fix above lets a live model actually bind correctly. **Confirmed live, first run after the fix**: `top_color`/`bottom_color` claims came back correctly grounded in the real image (`red`/`blue`), the plan step genuinely waited on them, `color_meaning_lookup` fired with the real claim values, and the FINAL was grounded in the tool's response — the full INTERPRET→VISION→PLAN→TOOL→COMPOSE path, live, working end to end for the first time. `tests/test_live_multimodal_orchestration.py` (5 new): `build_prompt` unit tests for both fixes (present/absent cases) plus one integration test that captures the real PLAN prompt `kernel/task.py` assembles (not just a hand-built view dict) and proves `pending_visual_targets` actually reaches it. 134/134 total (129 + 5), full suite + Docker not yet re-verified as of this write — see the footer Update Rule for the exact state when this was written.

**Third Phase 7 session: R-07/M-09/M-04 scenarios, which surfaced three real perception/ASR liveness bugs** (all reproduced on the pre-fix code before changing anything; each regression test verified to fail with the `src/` changes stashed and pass with them):

**C6 (Schema-Complete Read Sets)**, a cross-cutting correctness fix (`docs/prompt 3.txt` C6, tracked in `docs/post_v4_implementation_plan.md` line 57 as "◑ absence entries built (V2); read set still only covers bound params"), done rather than as part of the Phase 7 checklist above. Audited every read-set-construction path in the repo (confirmed complete by grepping for `build_read_set`/`ReadSetEntry(` across `src/`: `store/facts.py` — the mechanism itself; `kernel/executor.py` — tool calls; `kernel/frames.py` — FRAME; `kernel/task.py` — INTERPRET/PLAN/COMPOSE; `kernel/perception.py` — VISION; `kernel/audio.py` — ASR; nothing else in the tree builds one):
- **The gap**: V2's `absence_read_sets` mechanism (I-12) only tracked absence for a fact key the *Planner explicitly declared* via `step.absence_keys` — and nothing in `workers/planner.py`'s live prompt ever told a model this field existed, so in practice it was populated only by hand-written test plans, never a live plan. Every OPTIONAL tool-schema parameter a plan step's `bindings` simply didn't mention got zero read-set representation at all — a consumed result stayed valid even after the user later stated a value for it (the "omission escape" bug class, L2: "results consumed despite a later-set optional parameter in the same goal before FINAL").
- **Fix**: `PlanExecutor._schema_complete_absence_keys` (called from `_bind`, gated behind the existing `Config.absence_read_sets` flag) walks the tool's full JSON-schema `properties`, and for every parameter not already in `args` and not in the schema's `required` list, adds `slot.$G.<name>` to the call's read set — `build_read_set` resolves it to present-or-absent, whichever it currently is, reusing the exact I-12 mechanism instead of adding a new one. Required params are excluded (`validate_args` already guarantees they're bound by the time a call exists — a no-op, never a gap). **absence_sensitivity** (`docs/prompt 3.txt` C6 point 2: "policy default: user-sourced facts only") is implemented as a targeted exclusion — a slot name currently targeted by the goal's tracked perception question is skipped, since V3's own claim-acceptance path already governs exactly those names, and perception is the only non-user writer of `slot.<goal>.<name>` facts in this codebase; without the exclusion, a HIGH-confidence vision claim on an unrelated optional param would retroactively invalidate already-completed work, exactly the churn the doc calls out as the default to avoid. `is_valid`/`FactStore` themselves are untouched (would have been a global, unsound weakening) — the exclusion is applied only at the point new keys are added to a call's own read set.
- **Second instance of the same pattern, fixed at the abstraction level, not with a second conditional**: `kernel/frames.py.FrameScheduler.decide` (C2 response frames) built its read set from the goal's *currently-present* slots only, missing the same "unbound optional param" gap. Rather than duplicating the schema walk, it now folds the pending call's own `read_set.entries` into the frame's read set — the identical pattern `kernel/task.py._build_compose_request` already established for the same reason (`v10-1-correction-race-fix`) — so FRAME automatically inherits `_bind`'s completeness for free. COMPOSE itself needed no change; it already had this pattern from `v10-1`.
- **Audited, found already correct, left unchanged**: `_build_interpret_request`/`_build_plan_request` (`kernel/task.py`) track goal-level slot facts for INTERPRET/PLAN's own prompt context, not a fixed tool schema — the literal C6 mechanism doesn't apply to them the same way (no fixed parameter list to walk), and no gap was found. VISION (`kernel/perception.py.decide`, read set `["goal.active"]` only) is protected by a *different*, already-sound mechanism: staleness is enforced by `Question.pending_job_id` identity matching in `on_perception_result`, not by read-set validity — a retargeted question clears `pending_job_id`, so a stale VISION result's job_id no longer matches anything and is silently dropped, verified by reading `create_or_retarget_question`/`on_perception_result` together. ASR (`kernel/audio.py`, read set `[]`, documented "not goal-scoped") is correct as-is: a transcription's correctness is a pure function of the audio bytes, not of any fact/slot state.
- **Documented, deliberately out of scope**: `docs/prompt 3.txt` C6's own text also calls for goal-level constraints (that map to no tool parameter at all) to be tracked in FRAME's and result-selection steps' read sets specifically — this needs a registry of "constraint names considered but absent," which doesn't exist anywhere in this codebase (slot names are free-form, whatever the Interpreter extracts, not a fixed schema); building it would be a new mechanism, not the smallest fix, and is really C8's ("claim-typed atomic emission") territory (CS-06 overlay validation, itself unbuilt — see the Phase 7 audit above) more than this task's literal tool-schema invariant. Left undone, named here rather than silently skipped.

**CS-28 — the one real, fixed bug this audit found**: `docs/prompt 2.txt` line 370, the "Floor rule" — "No SPEAK, CLARIFY, or FINAL is emitted while the floor region is USER_TURN_OPEN (policy `speak_during_open_turn`, default OFF). Talking over the user harms naturalness and usually refers to soon-to-change information." Nothing anywhere checked `store.floor_state` before emitting any of these three action types — `CommitGate` G3 checks it, but only for *writes*. `kernel/responder.py.FastResponder`, the sole source of SPEAK/CLARIFY/FINAL in this codebase, spoke unconditionally the instant its own per-action trigger condition became true.
- **Reproduced twice, both ordinary (not contrived) scenarios**, by direct script before writing any test: (1) a goal's tool call takes real time to resolve; the user starts a second, unrelated utterance before it resolves (floor reopens, no EOT yet); FINAL still fired the instant the tool result landed, talking over the user's new sentence. (2) A write gets cancelled by a correction but its real result confirms late anyway (`CallStatus.COMPLETED_AFTER_CANCEL`, I-15's own scenario); if the user starts a new utterance before that late result arrives, the reconciliation notice ("the earlier booking had already gone through...") still fired mid-sentence. Neither needs interruption/cancellation machinery specifically — (1) is reachable in the most ordinary "slow tool call, user keeps talking" case.
- **Fix**: `FastResponder.decide` (`kernel/responder.py`) — the *only* source of these three action types (CANCEL/TOOL_CALL come from `InvalidationEngine`/`CommitGate` elsewhere, correctly untouched) — now returns `[]` immediately when `floor_state == USER_TURN_OPEN` and the new `Config.speak_during_open_turn` (default `False`, matching the doc's own stated default) is off. Returning early, before any of the method's own "already handled" facts (`ack.*`, `clarify.*`, `inform.*.sent`) get set, is what makes a floor-blocked notice *deferred* to the next step the floor closes rather than silently and permanently dropped — verified directly (both repro scenarios re-run post-fix: the notice/FINAL correctly waits, then fires the moment the floor closes again, confirmed via the exact `StepReport` of the step that closes it).

**M4 built — `sim/explorer.py` + `sim/minimize.py`.** Bounded, deterministic exploration: for each of 10 race scenarios (`tests/explore_scenarios.py`), seeded random schedules over realistic tool/worker latencies and user-event gaps, plus *targeted* schedules placing each tool result one step before/at/after each later user event (crossed with a 400ms interpreter). 9 oracles re-derived from state, not kernel helpers: full `TraceChecker`, floor rule, TRIAGE hold, FINAL grounding vs. consumed-call args, invalidated-never-cancelled, ≤1 confirmed write per lineage, liveness at an adaptive horizon, W4 reconciliation, per-scenario semantics. `minimize` is a 1-minimal delta-debugging pass (revert one knob at a time while the failure persists). Two oracle false positives were found and fixed before trusting any result (a fixed horizon too short for 3.2s tools; flagging inert PROPOSED leftovers of already-finished goals). First run: **126 of 471 schedules failing**, minimized to three real bugs:
1. **TRIAGE hold never built** (`docs/prompt 2.txt` §8.3, transitions 23-31; G3's "task state is not TRIAGE"; CS-15's "interpretation pending") — `kernel/task.py`'s docstring had deferred it. Minimal repro: search latency 400→220ms — the result lands while the user says "actually Mumbai", the CS-28 floor rule holds FINAL, then releases FINAL("Pune") in the very step the correction's EOT closes the floor, before the correction is interpreted. Second consequence: with INTERPRET slower than settle_ms (normal for a live model), `book_flight(F6)` passed every gate after the user said "no the 8pm one" — the L5 double-booking race the settle barrier was meant to close, reopened by model latency. **Fix:** `interpret_apply.interpretation_busy` (pending marker or a Phase 6 `eot_waiting` turn); while busy with an active goal, `FastResponder` emits nothing (watchdog salvage exempt) and `CommitGate` admits no new call of any kind (G3). Nothing is stored in a "hold": the kernel re-derives every output from state each step, so once the interpretation lands, whatever is still valid is emitted then and whatever it invalidated never is. `Config.triage_hold_enabled` (default on) exists so the explorer can demonstrate the effect.
2. **Rapid follow-up silently erased the first request.** A second turn closing before the first turn's INTERPRET returned *overwrote* `session.pending_interpretation_turn`; the first turn's result then failed `is_pending_this_turn` and was discarded — "Find flights to Pune" + "mm-hmm" (INTERPRET 400ms) produced no goal at all. **Fix:** `enqueue_interpretation`/`advance_interpretation_queue` — turns are interpreted strictly in order (`session.queued_interpretation_turns`); speculative promotion/eot-wait is skipped while an earlier turn is outstanding; `apply_interpretation` only consumes the marker for its own turn.

### Third ASR layer root-caused (Whisper CUDA OOM), GPU/RAM limits of this laptop, and the move to a cloud GPU (same session, later)
- **Root cause of the "STT event never fires" layer: `RuntimeError: CUDA failed with error out of memory` inside faster-whisper's encoder** (found by adding INFO logging to `voice/speech.py._recognize_impl`; `logging.basicConfig(level=INFO)` added in `voice/agent.py` so it shows in `docker logs`). `stt.StreamAdapter` swallows the exception and emits no transcript, so the kernel never learns the user spoke. Which recording fails varies run to run — a VRAM race, not a property of the clip (explains the identical audio stats found earlier). Cause: LiveKit's default PROCESS executor keeps a prewarmed spare job process, and each process loads its own Whisper + Kokoro, so two copies (~2.2–2.6 GB each) sat on the 8 GB GPU next to FDB's scorer. Committed in `27341a3`: `_recognize_impl` never raises (retries once, then returns an empty final transcript → Q6a re-ask), one `_GPU_LOCK` serializes Whisper and Kokoro inference, module-level model cache, and the scorer shim rewritten (below).

Running Parakeet on CPU moved ~5 GB into system RAM and got the terminal OOM-killed; on GPU its steady state is 2.5 GB, the OOM was a load-time double copy (~5 GB) that this avoids. Same fp32 precision as the organizers' scorer; transcript verified identical. `dev_livekit_run.sh` no longer sets `CUDA_VISIBLE_DEVICES=`.
- **THREAD job executor tried and rejected as the default.** Sharing one model copy across jobs (`JobExecutorType.THREAD`) fixed the OOMs (VRAM peak 7.8 → 6.4 GB, 0 OOMs), but a 26-recording run then had 2 FDB client aborts (`livekit_inference.py` exit -6, SIGABRT) and 3 recordings whose output audio was flat silence although the kernel emitted SPEAK/FINAL — clustered in later jobs (#7–#24), suggesting degradation in one long-lived shared process.
