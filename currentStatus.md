### Implemented
V0 + V1 (see git history / `v0-skeleton`, `v1-text-agent` tags) plus full V2 per `docs/sonnet_implementation_plan.md` §4 VERSION 2 / §5 Phase 16. All five V2 flags now default `True` in `Config` (`config.py`) — construct `Config(flag=False)` to get V1 behavior back for comparison:
- **Transitive invalidation** (`transitive_invalidation`): consuming a result now writes `derived.<gid>.<name>` facts from the plan step's `output_map`, tagged with the call's own read set as `Provenance.derivation_read_set`. `kernel/invalidation.py`'s fixpoint loop (max 8 rounds) retracts a stale derived fact and cascades to whatever read *it*, so a 2- or 3-step chain (search → derived flight → seat map / price → book) cancels every downstream call in the same step a slot changes. `PlanExecutor._bind`'s `STEP_OUTPUT` binding prefers the derived fact over the raw `result.<call_id>` when this is on.
- **Settle barrier** (`settle_barrier_enabled`): `CommitGate` gains G10 (settle_ms since `session.last_eot_ts`) and G11 (no newer turn open) for writes — catches "book the 6pm one" → 200ms → "wait, the 8pm one" before the first booking ever goes out. New `store/ledgers.py` `TimerWheel` + `StepReport.next_wake_us` are a pure liveness hint (T-05) — no correctness depends on a timer firing; a blocked call is just re-evaluated every step like always.
- **Rebinder** (`rebinder_enabled`): `interpret_apply._can_rebind` — a slot change stays in `EXECUTING` instead of forcing a full replan when every affected step is FACT-bound to it and none has `structure_depends_on` including it (§8.4). Zero Planner round-trip for a purely local correction.
- **Absence read-sets** (`absence_read_sets`): `PlanStep.absence_keys` — a step can declare an optional fact it assumes is unset; `PlanExecutor._bind` adds an `ABSENT` read-set entry for it, so adding that fact later ("only direct flights") invalidates the call through the ordinary mechanism with no new machinery.
- **Claim grades** (`claim_grades_enabled`) + **reconciliation** (unconditional, not gated — a safety property): `FinalBody`/`SpeakBody.claim_grade` (UNDERSTOOD/INTENDED/RESULT/EFFECT_DONE); an INTENDED-graded utterance while a write sits behind G10; and `FastResponder._reconcile_completed_after_cancel` truthfully reports a write that completed (or whose outcome is unknown) despite being cancelled (W4, I-15).

V3 (multimodal grounding) per `docs/sonnet_implementation_plan.md` §4 VERSION 3 / §5 Phase 17, gated entirely behind `Config.vision_enabled` (default `False`) plus two new flat-timeout knobs (`evidence_align_window_ms`, `evidence_lease_ms`) — every new code path is a documented no-op when the flag is off, so V0-V2 are structurally unaffected (proved by all 36 V0-V2 tests passing unchanged):
- **New module `kernel/perception.py`** (`PerceptionScheduler`): the whole V3 lifecycle in one place — `create_or_retarget_question` (called from `kernel/interpret_apply.py` when an accepted interpretation's `visual_reference` is set — the only question-creation trigger implemented; QuickDetector-cue and plan-declared triggers from the full spec are deliberately not wired, see the module's own docstring), `decide` (frame alignment + VISION job dispatch, called from `kernel/step.py`'s DECIDE phase alongside `TaskStateMachine`), `on_perception_result` (claim acceptance — HIGH promotes to a `slot.<goal>.<name>` fact when no conflicting user value exists, MEDIUM/LOW never do), and `expire_leases` (a flat-timeout lease check run every step, gated no-op when vision is off, that retracts a stale `CURRENT_STATE` claim through the *ordinary* fact-retraction/invalidation path — no new cancellation machinery needed).
- **`store/ledgers.py` `EvidenceStore`**: observations (frames, always stored, analyzed only on demand), one active `Question` tracked per goal, one open `Conflict` tracked per `(goal, name)` — simplified from the full spec's per-question/multi-conflict bookkeeping (see `model/types.py`'s V3 section docstring for the exact list of cuts).
- **Conflicts** (`docs/prompt 2.txt` §9.1): a HIGH/MEDIUM perception claim that disagrees with an existing *user-sourced* slot value opens a `Conflict` instead of overwriting it; `kernel/executor.py`'s `PlanExecutor._bind` blocks any step bound to that slot (reusing the exact same "missing key → clarify" path V1 already had for unfilled slots — no new gate); `kernel/responder.py`'s `_clarify` recognizes an open conflict and names both candidate values instead of the generic template. A later user statement on that slot name voids the conflict (`interpret_apply._apply_slot_deltas`).
- **`$Q` plan-binding substitution**: `PlanStep.bindings` may reference `claim.$Q.<name>` the same way `$G` already substitutes the goal id — `PlanExecutor._bind` resolves it to the goal's current question id. Used specifically for `CURRENT_STATE` targets (so a lease-expiry retraction is recognizable by its `claim.` key prefix and triggers a silent re-fetch rather than an `_ask_for` clarify — see the scope-trim note in `executor.py`); `AT_UTTERANCE` targets bind through the ordinary `slot.$G.<name>` path instead, since that's what makes the conflict-blocking check apply.
- **`workers/vision.py`** (`VisionAnalyzer`): same `ScriptedProvider`-mocked worker pattern as Interpreter/Planner/Composer. The frame is passed by reference (`obs_id`) only — the existing `Provider.complete_json(kind, prompt, schema)` protocol is text-only (see `workers/gateway.py`'s `GeminiProvider`, added earlier this session for the same reason), so no test or live path here actually sends pixel data; a real image-grounded call would need a second, image-aware `Provider` method, out of scope.

**Post-V4 Phase 4 (Interruption-Recovery Depth — CHUNK Anchor)** per `docs/post_v4_implementation_plan.md` — every prior version's cancellation was EOT-anchored (a correction only took effect once the turn closed and a fresh interpretation committed a changed slot); this adds the earlier CHUNK anchor from `docs/prompt 2.txt` §8.2, no new cancellation machinery:
- **`kernel/detector.py.QuickDetector.detect_values`**: HIGH-confidence slot-value extraction — exact schema-enum match, and session-entity match (a value already seen this session for exactly one slot name). §9.2's date/time and bare-number extractors are a documented scope trim (this project's tool schemas never exercise the disambiguation they'd need).
- **`store/session.py.StoreTxn.mark_chunk_anchor(key)`**: feeds a slot's key into the *same* `changed_keys()` → `InvalidationEngine` pipeline a real fact change uses, without ever calling `facts.set()` on the slot — the slot's committed value/digest stay untouched; only its dependents (in-flight/proposed calls in `DependencyIndex`) get cancelled, in the same step. `kernel/turns.py.TurnManager._detect_chunk_anchor` calls it only when a HIGH value differs from the slot's current committed value (a revert-safety skip when it already matches) and the chunk-anchor context holds (interruption, active goal, or a correction cue) — `docs/prompt 2.txt` §8.2's precise rule. **Post-V4 Phase 5 (Task-Completion Depth — C2 Response Frames + C9 Commit-Last Ordering)** per `docs/post_v4_implementation_plan.md`, targeting the 40%-weighted scoring category:
- **C2 response frames** (`kernel/frames.py.FrameScheduler`, `workers/frame.py`, `Config.frame_rendering_enabled`, default `False`): a `JobKind.FRAME` job dispatches the moment the plan's *last required call is emitted* (in flight, not yet resolved) — the model writes a template with typed holes (`field`/`count`/`min`/`max`/`first_k`/`exists`, bound to result paths) using only the tool's declared output schema and the goal's facts; no result data ever reaches it. The instant that call's real result is consumed, `try_render` selects a branch (`success`/`empty`, by whether the declared `list_path` resolves to `[]`), evaluates every hole deterministically against the actual result, and — only if every hole resolves — writes `compose.<goal>.text` directly, the exact fact Composer would have written, so `kernel/responder.py`'s FINAL emission needed zero changes. `kernel/task.py`'s EXECUTING branch skips the redundant COMPOSE dispatch only when that fact is already set, so Composer is always the fallback (no provider rule, a hole that fails to evaluate, or a stale frame) — never bypassed silently. The frame's read set (goal facts at dispatch time) is checked at render time via `Provenance.derivation_read_set`, so a correction drops it, verified directly.
  - **Scope trim** (documented in `kernel/frames.py`'s module docstring): only `success`/`empty` are ever selected; `error` is parsed/validated but never chosen, since `kernel/results.py.ResultRouter` routes an error result to `CallStatus.FAILED` (retried, not terminal) rather than `CONSUMED` — wiring the `error` branch needs `PlanExecutor._fail_goal`'s goal-failure path, out of scope here.
- **C9 commit-last ordering** (`kernel/executor.py.PlanExecutor._commit_last_blocked`, `Config.commit_last_ordering`/`commit_last_wait_cap_ms`, default `False`/3000): a WRITE step, even once its own `after` dependencies are satisfied, waits for every READ step in the plan that isn't downstream of it (a sibling/independent read) to resolve first — bounded by the wait cap so a slow unrelated read can't block a write forever. Verified against N-02b: `book_flight` doesn't emit before an independent `get_weather` read resolves with the flag on, emits promptly with it off, and the cap releases it once elapsed regardless.
- `tests/test_phase5.py` (11 new): 4 for C9 (blocked/unblocked/wait-cap/replay), 7 for C2 (grounded success FINAL with zero COMPOSE dispatch, empty-branch selection, two Composer-fallback paths, flag-off parity, a whitebox stale-frame-rejection test, replay identity).

**Post-V4 Phase 6 (Response Latency — Speculative Interpretation + Content-Bearing ACK)** per `docs/post_v4_implementation_plan.md`, targeting the 15%-weighted scoring category, `docs/prompt 2.txt` §11.3:
- **Speculative interpretation coalescing** (`kernel/task.py.TaskStateMachine._speculative_interpret`, `Config.speculative_interpretation_enabled`, default `False`): while a turn is open, at most one INTERPRET job runs per turn, dispatched against the current prefix; a growing prefix doesn't spawn a second job, it just makes the completed one's cached digest stale (redispatched against the latest prefix once noticed, on the very next DECIDE phase). A speculative job's read set deliberately excludes `session.pending_interpretation_turn` (only a non-speculative, post-EOT dispatch includes it) — the read-set subtlety flagged by the earlier plan file: including it would make the turn later closing (which sets that fact) self-invalidate the very job this mechanism exists to promote.
- **EOT promotion** (`kernel/turns.py.TurnManager._try_promote_speculative` / `_mark_eot_waiting_if_matching_job_in_flight`, `kernel/reducers.py._cache_speculative_interpretation`): a resolved speculative job is cached (digest + raw proposal), never applied immediately. At EOT: a cached result whose digest matches the turn's final prefix is applied in the *same step* as EOT — zero additional model latency. A still-running matching job (digest still valid per the ordinary read-set check) is waited for instead of triggering a redundant second dispatch — `_apply_worker_result`'s INTERPRET branch applies it directly once it resolves. Anything else (no cache, stale cache, no matching in-flight job) falls back to today's non-speculative EOT-anchored dispatch, unchanged.
- **Content-bearing ACK** (`kernel/responder.py.FastResponder._content_ack_text`, §9.3): the plan-dispatch ACK names the HIGH-confidence value QuickDetector recorded (a `hyp.<turn>.<name>` fact, Phase 4's `detect_values`) for the turn that triggered it, instead of the fixed generic string — e.g. `"Got it — destination: Mumbai."` Since Phase 4's `_detect_chunk_anchor` writes that fact unconditionally regardless of whether a goal existed yet, this covers a brand-new first utterance exactly as well as a correction on an active goal; when QuickDetector found nothing HIGH-confidence, the generic string is used (verified directly, not assumed — an earlier draft's docstring wrongly claimed a narrower scope until testing showed otherwise).
- **Real measured latency win, in `docs/measurements.md`**: on a T-06-shaped scenario (INTERPRET latency 300ms, chunk spacing 150ms — the blueprint's own numbers), TTFS(EOT) drops from 300,000µs (flag off) to 0µs (flag on) — a 100% reduction, meeting T-06's acceptance bar.
- **Not built (documented, not silently skipped)**: full inert-tail promotion (C1/M-02 — a promoted interpretation may differ from the final text only by a trailing filler word like "please"; this phase's promotion is exact-digest-match only, a strict, faithful subset of §11.3's literal spec). The speculative-dispatch infrastructure this phase builds is the prerequisite inert-tail promotion would sit on top of, making it a smaller follow-up than before rather than needing a new subsystem. Also not built: speculative planning, speculative multimodal processing, and the two OFF-by-default speculative-read classes from §11.1's table — all real, all lower-value than interpretation coalescing for this project's scenario mix, and none blocking a safe submission.

**Four more real bugs found and fixed in Phase A + Phase 2** (on top of the eight from V1/V2 — all from writing tests against the real kernel/entry point, none from design review):
1. Dataclasses don't validate field types at construction — `TextChunkPayload(text=12345)` built successfully and only crashed later, deep inside `TurnManager.on_chunk`'s `" ".join(...)` over chunk text. 4. `TurnManager.on_eot` closing a turn was silently insufficient to trigger interpretation — the actual `session.pending_interpretation_turn` marker only ever got set inside the `end_of_turn` reducer, never inside `TurnManager` itself. First discovered when an audio-only (N-06) manual test produced no goal at all. Fixed by extracting a `TurnManager.request_interpretation()` method both call paths now share.

**Five more real kernel bugs found and fixed while writing the V2 tests** (on top of the three found during V1 — eight total across the project, all from writing tests against the real kernel, none from design review):
1. `PlanExecutor` treated `CONSUMED` as "done forever" for a step_key regardless of whether the facts it read had since changed — contradicting the architecture's own §3.5 carry-over rule ("a step carries over only while its resolved arguments are unchanged"). A corrected step never re-ran; everything downstream silently bound to pre-correction data. Fixed: both `propose_ready_calls` and `_step_done` now check the consumed call's read-set validity, not just its status.
2. The same bug's sibling: a `PROPOSED`-but-not-yet-admitted call (e.g. blocked behind settle) could also go stale before ever being emitted, and was left blocked forever failing G2 for the wrong reason. Fixed identically — replace it if its read set has gone stale, mark the old one `DISCARDED`.
3. `CANCEL_REQUESTED` calls blocked their own replacement's proposal until the stale call's late result formally resolved it (~800ms later in one repro) — defeating same-step cancellation's entire purpose. Fixed: `CANCEL_REQUESTED` now gets an immediate fresh attempt, uncounted against retry limits.
4. Calls never included `goal.active`/`catalog.version` in their read set (architecture spec §4.4 calls for this explicitly) — so ABORT never invalidated in-flight calls. Fixed the read set; `_abandon_goal` also directly invalidates (since `goal.active` must stay pointing at the abandoned goal so FastResponder can still speak the final "cancelled" message), and `InvalidationEngine.cancellation_actions` now scans the ledger for any `INVALIDATED` call rather than only what its own fact-diff pass found this step.
5. `TraceChecker`'s own S3 and W1 checks had false positives (compared a snapshot against *final* state instead of state-as-of-that-step; flagged legitimate write retries as duplicates). Both fixed to check the actual invariant.
